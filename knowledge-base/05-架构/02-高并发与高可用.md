# 高并发与高可用

## 基础知识

### 先定义指标

- QPS/RPS：每秒请求数。
- TPS：每秒完成的业务事务数，口径必须说明。
- 并发数：同时在系统中的请求或连接数。
- 延迟：关注 p50、p95、p99，不只看平均值。
- 错误率：按错误类型和业务结果统计。
- 饱和度：CPU、内存、连接池、线程/进程池、队列和磁盘。

Little's Law 在稳定系统中近似为：

```text
并发数 = 吞吐量 × 平均停留时间
```

例如 700 RPS、平均响应 40ms，对应平均在途请求约 28，不等于必须有 700 个 PHP worker。真实系统还要看分布和长尾。

### 三个基础容量公式

#### CPU 上限

```text
CPU 容量（RPS）≈ CPU 核数 × 目标利用率 / 单请求 CPU 时间（秒）
```

8 核、目标 70%、单请求平均 CPU time 8ms：`8 × 0.7 / 0.008 ≈ 700 RPS`。

#### 并发与等待

```text
在途并发 ≈ RPS × 平均响应时间
```

700 RPS、40ms 得到约 28 个平均并发。如果 p99 为 1 秒，峰值所需 worker/连接会远高于平均值，容量必须结合延迟分布。

#### 内存上限

```text
进程上限 ≤ 分配给进程池的可用内存 / 单进程峰值 RSS
```

给 FPM 6GiB、单 worker 峰值 60MiB，纯内存上限约 102；还应预留 master、Nginx、系统页缓存、监控和突发空间，实际 `max_children` 要更低，并受 CPU/数据库连接限制。

### 排队为什么会突然恶化

当到达率接近服务率，少量抖动就会形成队列，等待时间非线性增长。CPU 100%、FPM worker 全忙或数据库连接池满时，新增请求没有计算资源，只会排队并扩大超时/重试。

因此常把目标利用率留在 60%-75% 等可恢复区间；具体值由延迟目标、流量波动和扩容速度实测决定，不是统一标准。

积压增长可用一个简单模型预警：

```text
backlog_growth_per_second = arrival_rate - service_rate
recovery_time ≈ backlog / (recovery_service_rate - new_arrival_rate)
```

生产 1000 条/s、消费 700 条/s，10 分钟会积压约 `300 × 600 = 180000` 条。若流量恢复为 500 条/s、消费者仍处理 700 条/s，理论清空至少需要 `180000 / 200 = 900s`，还未计失败重试和下游限流。

### 扩展方式

- 纵向扩展：升级单机 CPU/内存/磁盘，简单但有上限。
- 横向扩展：增加实例，需要无状态、负载均衡、数据分布和自动化。
- 功能拆分：把静态、应用、缓存、数据库、搜索和任务分离。

### 可用性

99.9% 月度不可用时间约 43.8 分钟，99.99% 约 4.38 分钟。必须定义统计窗口、请求口径和计划维护是否计入。

冗余只有在故障独立、能检测并切换时才提高可用性。两台共享同一电源、网络或数据库的服务器仍可能同时失败。

## 高阶知识

### 限流、熔断、降级、隔离

- 限流：控制进入速率，保护容量。
- 熔断：依赖持续失败时快速失败，避免级联占用。
- 降级：舍弃非核心功能或返回缓存/简化结果。
- 隔离：按依赖/租户分连接池、队列或资源，限制故障半径。

熔断不是重试替代品；重试会放大流量，应受重试预算限制。

### 缓存风险

- 穿透：查询不存在数据。校验、空值缓存、布隆过滤器。
- 击穿：热点键失效。互斥回源、逻辑过期、预热。
- 雪崩：大量键同时失效或缓存整体不可用。TTL 抖动、多级缓存、限流和回源容量保护。
- 一致性：明确可容忍窗口，使用删除缓存、版本号、CDC 和对账。

### 负载均衡

- 四层：基于连接/IP/端口，性能高。
- 七层：理解 HTTP，可按域名、路径、Header 路由。
- 算法：轮询、加权、最少连接、一致性哈希等。

`ip_hash` 不是可靠会话方案：NAT、大型代理、节点变化都会影响分布。优先把会话外置或使用有过期和容灾策略的粘性会话。

### 发布与容灾

- 滚动发布：逐批替换实例。
- 蓝绿发布：两套环境切换。
- 灰度/金丝雀：少量流量验证后扩大。
- 多可用区：防单机房故障。
- 备份恢复：必须定期演练 RPO/RTO，而不是只确认“有备份文件”。

RPO 是可容忍的数据丢失窗口；RTO 是可容忍的恢复时间。

故障域要从共享依赖判断，不从实例数量判断：两个应用实例若共享同一宿主机、交换机、数据库或配置错误，仍可能一起失败。跨可用区会增加网络延迟和费用，也必须验证数据复制与切换策略。

## 使用案例

### 8 核服务器 700 RPS 时 CPU 70%

不能只用 Nginx access log 的 30-40ms 总响应推导 CPU 理论值。应采集：

1. 每请求 CPU time，而非 wall time。
2. FPM active/idle/listen queue。
3. Nginx upstream time。
4. 数据库/Redis/外部 API 延迟。
5. 进程上下文切换和 GC。

若 700 RPS 消耗 5.6 core-seconds/s，则平均 CPU 约 8ms/request。30-40ms wall time 的其余部分可能在等待 I/O，也可能统计口径不同。

进一步估算：平均响应 40ms 对应约 28 个在途请求。若配置 250 个 FPM worker，而长期只有约 28-50 个活跃，则继续增加 worker 不会提高吞吐；反而可能增加内存、数据库连接和上下文切换。真正需要对比的是 FPM `max active`、listen queue、每请求 CPU time 与下游等待。

### 秒杀/抢券

```text
网关限流
→ 身份与资格校验
→ Redis/Lua 原子预扣
→ 队列削峰
→ 数据库幂等落单
→ 失败补偿/对账
```

不能只靠“把 100 张券分成 10 个 key”保证正确；必须处理重复请求、库存不超卖、消息重复、落库失败和补偿。

### 故障演练

定期验证：杀应用实例、停止 Redis 副本、模拟数据库只读、增加网络延迟、让队列积压、执行备份恢复。演练必须有停止条件和业务保护。

## 常见问题与排查

- 增加实例后不加速：瓶颈在数据库、锁、外部依赖或负载不均。
- 延迟长尾：检查队列、GC、慢 SQL、连接池等待、重试和少量大请求。
- 故障转移数据丢失：异步复制未追平，需根据 RPO 选择半同步、共识系统或业务补偿。
- 缓存故障拖垮数据库：设置回源限流、熔断和容量预案。

## 版本边界与学习验收

Little's Law、排队、冗余和故障域不依赖具体产品；负载均衡算法、自动扩缩容指标、复制协议和云故障模型会随平台变化。所有“单机支持多少 QPS”和推荐利用率都必须绑定硬件、版本、请求模型与压测条件。

验收：用 CPU、内存、Little's Law 和积压公式预测容量；逐步压测到 p99 非线性上升；注入缓存不可用、依赖超时、消息积压和单区故障，验证限流、降级、恢复时间和数据正确性。
