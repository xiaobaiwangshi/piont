# 架构基础

## 基础知识

架构是在约束下组织系统，使其满足功能和质量目标。没有流量、数据量、延迟、可用性、成本和团队能力等约束，谈“最佳架构”没有意义。

### 质量属性

- 性能：延迟、吞吐、资源效率。
- 可用性：在约定时间内提供正确服务的比例。
- 可靠性：持续正确工作的能力。
- 可扩展性：增加功能时控制修改成本。
- 可伸缩性：增加资源时提升容量。
- 安全性：机密性、完整性、可用性和审计。
- 可维护性：理解、修改、测试和发布的成本。

这些属性存在冲突。例如同步强一致通常增加延迟；冗余提高可用性但增加成本和一致性复杂度。

### 从约束到组件

架构设计按因果顺序推进：

```text
业务目标与 SLO
→ 流量、数据量和增长
→ 一致性、延迟与恢复目标
→ 当前瓶颈和故障域
→ 最小机制/组件
→ 观测、演练和退出方案
```

| 问题 | 常见机制 | 新成本 |
|---|---|---|
| 热点读取压垮数据库 | 索引、缓存、只读副本 | 一致性、失效、复制延迟 |
| 峰值写入超过处理能力 | 批处理、队列、背压 | 积压、重复、最终一致性 |
| 单实例故障 | 多实例、健康检查、故障转移 | 状态外置、切换误判、成本 |
| 数据量超过单节点 | 分区/分片 | 跨分片查询、迁移、热点 |
| 依赖抖动拖垮调用方 | 超时、隔离、熔断、降级 | 失败语义、数据补偿 |

组件名称不是设计结论。每次引入都要写“解决的问题、假设、容量上限、失败方式、观测指标和移除条件”。

### 分层与模块化

常见服务端分层：

```text
HTTP/Transport
→ Application/Use Case
→ Domain/Business Rules
→ Infrastructure
```

分层的目标是控制依赖和变化，不是让每个请求机械穿过大量空壳类。简单 CRUD 可以保持简单；核心业务规则需要明确边界和测试。

### 单体与微服务

优先模块化单体：部署、事务、调试和本地开发简单。当出现独立扩缩容、团队自治、发布节奏或故障隔离的真实需求，再按业务边界拆服务。

微服务会引入网络故障、分布式数据、链路追踪、服务发现、版本兼容和运维平台成本。代码目录拆开不等于获得这些能力。

## 高阶知识

### 状态与无状态

应用实例尽量无状态：会话、任务和文件存入共享且可靠的系统，使负载均衡能把请求发往任意实例。无状态不代表系统没有状态，而是实例本地不持有不可替代状态。

### 同步与异步

- 同步调用：结果立即参与当前流程，语义直接，但耦合延迟和可用性。
- 异步消息：隔离峰值和失败，支持重放，但引入最终一致性、重复和积压。

只有无需立即返回结果、能够定义状态和失败补偿时才异步化。

### CAP 与一致性

CAP 讨论发生网络分区时，一致性和可用性的取舍；P 不是日常可以关闭的按钮。它不等同于“数据库只选两个”，也不直接描述单机 ACID。

工程上还需明确：

- 读己之写、单调读、因果一致或线性一致。
- 数据允许多长时间不一致。
- 冲突如何检测、合并和修复。

### 唯一 ID 与时间

- 数据库自增：简单、有序，跨库需协调。
- UUID：分布式生成方便；随机 UUID 作为聚簇主键会增加页分裂，可选择有时间局部性的 UUIDv7 等方案。
- Snowflake 类：趋势有序、高吞吐，但需要节点 ID 和时钟回拨处理。

“毫秒时间戳优于 UUID”是不成立的泛化结论：时间戳会碰撞，也泄露时间信息。根据唯一性、排序、隐私和存储选择。

## 使用案例

### Web 系统演进

```text
单机 LNMP
→ 静态资源上 CDN/对象存储
→ 应用多实例 + 负载均衡
→ Redis 缓存/会话
→ MySQL 主从和备份
→ 队列异步任务
→ 搜索引擎
→ 按真实瓶颈拆服务
```

每一步都应有指标证明当前瓶颈，并给出回滚方案。不要一次性搭建终局架构。

### API 边界

接口应定义：请求/响应 Schema、错误码、幂等、认证、超时、限流、版本兼容和弃用策略。REST、RPC 只是传输风格，无法替代业务边界设计。

### 数据所有权

每类核心数据有唯一权威写入方。其他服务通过 API、事件或只读视图使用，避免多个服务直接修改同一表导致规则失控。

## 常见问题与排查

- 系统耦合：先找共享数据库、双向调用和共同发布点，再调整边界。
- 分布式事务：优先缩小一致性边界；再用 outbox、Saga、幂等和补偿。
- 架构过重：删除没有消费者的事件、单实现抽象和无指标支撑的组件。
- 数据漂移：建立对账、版本号、重放和重建能力。

## 版本边界与学习验收

分层、异步、缓存、冗余、分区和质量属性是稳定思想；服务网格、注册中心、云产品和部署拓扑属于时代与团队约束。旧架构书中的具体产品清单只作历史案例，不作为现代默认答案。

验收：为一个实际 Web 服务写出 SLO、峰值流量、数据增长、RPO/RTO、三个主要故障域和容量公式；每个拟引入组件必须能说明收益、成本和失败时的回退路径。
