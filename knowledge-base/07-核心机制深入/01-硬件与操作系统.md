# 硬件与操作系统核心机制

本文从“程序为什么会以现在的速度和方式运行”出发，连接计算机组成原理与 Linux。

数据表示、CPU 时间、Amdahl、Cache 地址/AMAT、虚拟页与页表估算先见[计算机组成原理](../01-基础/01-计算机组成原理.md)和[操作系统](../01-基础/03-操作系统.md)。本章不重复公式，重点追踪状态怎样穿过微架构与内核；命令仅作观察入口，本阶段不要求执行。

## 表示层与机器执行边界

整数范围、IEEE 754 和字节序的定义见主章节。进入 CPU 后，寄存器和内存保存的只是固定位宽 bit pattern，由具体指令决定它被解释为有符号整数、无符号整数、浮点数或地址。相同位模式采用不同指令会产生不同结果，类型信息通常由编译器和程序语义维护，而不是附着在每个内存字节上。

端序影响多字节值在内存中的字节排列，不改变寄存器内部的位编号，也不决定 UTF-8 等协议编码。跨网络、文件和外设边界时，软件必须显式遵守规定的字节序和数据布局。

## 指令、流水线与分支

ISA 定义软件可见的指令和寄存器；微架构决定 CPU 如何实现 ISA。现代 CPU 会取指、译码、重命名、乱序执行并按程序顺序提交结果。

流水线风险：

- 数据相关：后续指令依赖前一结果。
- 控制相关：分支方向未知。
- 结构冲突：多个操作争用执行资源。

分支预测错误会丢弃推测执行结果并重新填充流水线。高度不可预测的分支、间接调用和数据依赖链会降低每周期完成指令数；这解释了为什么相同 Big-O 的两段代码速度可能相差很大。

### 从乱序执行到顺序提交

可把常见乱序核心抽象为：前端取指/预测和译码，重命名消除部分假相关，调度器把操作发往执行单元，load/store 单元访问缓存，最后由重排序缓冲等结构按程序顺序提交架构状态。具体结构因 CPU 而异，但“内部可投机，提交点保持精确状态”是理解精确异常的关键。

发生分支预测错误时，错误路径的未提交结果被丢弃；发生缺页等精确异常时，较老指令已提交，出错及更年轻指令尚未改变架构可见状态。进入内核处理后，指令可能重试、向进程发送信号或终止。

## CPU Cache

### 从一次访问到缓存事务

Cache line、组相联、地址拆分、未命中类型和 AMAT 见主章节。load/store 发出虚拟地址后，地址翻译与 Cache 查询在具体 CPU 中可能部分重叠；命中时从目标 line 取得或修改数据，未命中时向更低层请求 line，并可能先回写被替换的脏 line。

多级 Cache 并非简单的三个独立字典：包含关系、共享层级、受害缓存、预取器和未完成 miss 跟踪结构均随微架构变化。多个 miss 可以并行挂起，因此观察到的停顿不一定等于 `miss 数 × 单次内存延迟`；依赖链、内存级并行和带宽共同决定结果。

### False Sharing

两个线程修改不同变量，但变量位于同一 cache line，会引发缓存一致性反复失效。症状是业务没有显式锁却扩核变慢。解决方式是减少共享写、按线程分片或在确认瓶颈后做对齐/填充。

### 一致性状态与内存顺序

MESI 一类协议可用 Modified/Exclusive/Shared/Invalid 等状态描述 cache line 的所有权与共享关系。一个核心要写共享 line，通常先取得独占所有权并使其他副本失效；频繁跨核写会制造一致性流量。真实 CPU 可能使用更复杂协议，状态名不是软件接口。

一致性回答“同一地址的缓存副本怎样收敛”，内存顺序回答“不同内存操作允许以什么顺序被其他执行者观察”。store buffer、无效化队列、编译器优化和 CPU 重排使软件必须通过语言定义的锁、原子和内存屏障建立顺序，不能依赖观察到的偶然时序。

## 虚拟内存深入

### 页表与 TLB

虚拟地址经多级页表翻译成物理地址。TLB 缓存近期映射；TLB miss 需要 page walk。大页可减少 TLB 压力，但增加内存浪费、分配和回收复杂度，不应盲目开启。

一次 TLB miss 但映射有效的访问，硬件或体系结构定义的软件处理流程会读取多级页表项，最终把翻译装入 TLB；这不等于 page fault。只有页表状态表明映射缺失、权限不符或需内核介入时，才进入缺页异常路径。

修改页表后，内核还要处理 TLB 中的旧翻译。单核可局部失效，多核共享地址空间可能需要向其他 CPU 发出 TLB shootdown；频繁映射变化或大范围 `munmap` 会产生跨核协调成本。

### 缺页

- Minor fault：映射可在内存中完成，无需磁盘读取。
- Major fault：需要从磁盘/远端存储载入，延迟高。
- Copy-on-write fault：fork 后首次写共享页时复制。

RSS 是当前驻留物理内存；VSZ 是虚拟地址空间规模，不能直接当作真实内存占用。

### NUMA

多路服务器的内存访问距离不同。本地 NUMA 节点内存更快；线程迁移、跨节点共享和不均匀分配会影响延迟。先用 `numactl --hardware`、性能分析和真实负载确认，再做绑核/绑内存。

## 调度与上下文切换

调度器在可运行任务间分配 CPU。不同内核版本的公平调度实现会演进，不必死记单一算法；需要理解的是运行队列、优先级、时间片/虚拟运行时间、唤醒和迁移。

上下文切换可能包含寄存器、调度器、缓存和 TLB 成本。`vmstat`/`pidstat -w` 显示切换数量，但“数量高”不是根因，需要结合线程数、阻塞点和吞吐变化。

### 阻塞、唤醒与运行队列

线程等待锁、socket、页或设备时，会把自己挂到相应等待结构并离开可运行队列；条件满足后，持锁代码、中断下半部或其他内核路径将其唤醒并重新入队。唤醒不等于立刻执行，还要等待 CPU、优先级和调度决策。

大量线程同时被唤醒会形成惊群或运行队列突增。事件循环、分片等待队列和内核的排他唤醒等机制可减少无效竞争，但最终要用运行队列长度、上下文切换、锁等待和有效吞吐共同判断。

### 锁、原子与睡眠边界

用户态互斥锁在无竞争时可主要通过原子指令完成；有竞争时再借助 futex 等内核机制睡眠和唤醒，避免一直占用 CPU。自旋锁适合预期极短、不能睡眠的内核临界区；临界区变长时自旋会浪费核心。

锁不仅排斥并发访问，还通过语言和体系结构规定的 acquire/release 语义传播可见性。无锁算法必须同时处理原子性、顺序和对象生命周期，ABA 与安全内存回收使其远比“把锁换成 CAS”复杂。

## 系统调用与 I/O 路径

```text
用户代码 read()
→ 进入内核
→ VFS
→ 文件系统/页缓存
→ 块层
→ 设备驱动
→ SSD/HDD
```

路径命中 page cache 时，读取可在内存完成；未命中时，文件系统建立块映射并向块层提交请求，驱动把请求交给设备。调用线程可睡眠，设备 DMA 完成后通过中断/轮询推动完成，内核标记页可用并唤醒等待者，`read` 才把结果交回用户态。

写入 buffered I/O 时，`write` 通常先复制到 page cache 并标脏。后台 writeback 或内存压力推动脏页经文件系统和块层下刷；`fsync` 把调用方纳入等待链，要求相关数据和必要元数据达到文件系统/设备声明的持久边界。journal 的提交、数据写入和设备 flush 次序由文件系统模式决定。

页缓存让普通文件读写先使用内存；`fsync` 请求把必要数据推到持久介质，但最终保证还取决于文件系统、设备缓存和硬件。

- Buffered I/O：使用页缓存，通用且简单。
- Direct I/O：绕过大部分页缓存，需要对齐和自行管理缓存，数据库可能使用。
- `mmap`：把文件映射到地址空间，访问通过缺页载入。
- `sendfile`：在内核数据路径中发送文件，减少用户态复制。
- `io_uring`：现代 Linux 异步 I/O 接口，适合经过验证的高 I/O 场景，不是所有程序的默认必选。

### 设备完成、中断与 DMA

以网卡接收为例，可把路径简化为：设备把数据 DMA 到内存环形缓冲区 → 触发中断或轮询通知 → 驱动和网络栈批量处理 → socket 变为可读 → 等待线程被唤醒。高负载时 Linux 会用中断缓和与 NAPI 式轮询减少每包中断成本。

因此 CPU 高不一定是业务计算：大量小包、中断分布不均、软中断积压、内存复制和协议栈处理也可能消耗 CPU。可结合 `/proc/interrupts`、`/proc/softirqs`、网卡统计和 profiler 判断。

块设备也遵循相似职责链：驱动建立描述符/队列 → 设备 DMA 读写内存 → 完成中断或轮询 → 块层和文件系统完成请求 → 唤醒等待线程。IOMMU 可限制设备可访问的内存并提供地址转换，但会增加映射和翻译成本；具体是否启用及开销取决于平台。

## 容器的操作系统基础

容器不是轻量虚拟机内核：

- Namespace 隔离进程、网络、挂载、用户等视图。
- cgroup 限制和统计 CPU、内存、I/O 等资源。
- Union/overlay 文件系统组织镜像层。

容器内看到的 CPU/内存可能受 cgroup 限制；应用运行时若只读取宿主机资源，可能配置过多线程或堆内存。

namespace 改变“看见什么”，不自动限制资源；cgroup 改变“最多可用多少、如何统计和调度”，不提供完整安全边界。用户 namespace、capability、seccomp、LSM 和只读挂载等共同缩小权限，不能只依赖 PID namespace。

cgroup v2 使用统一层级协调控制器。CPU quota 可能产生周期性 throttling，memory.max 等限制可在 cgroup 内触发回收/OOM，I/O 控制依赖设备和调度支持。字段与默认行为随内核和容器运行时变化，应按目标环境解释。

## 观察思路与命令示例

```bash
lscpu
getconf LEVEL1_DCACHE_LINESIZE
perf stat -e cycles,instructions,cache-references,cache-misses ./your_program
vmstat 1
pidstat -u -r -w -p "$PID" 1
```

重点指标：IPC=`instructions/cycles`、cache miss、page fault、上下文切换、CPU migration。性能实验需固定输入、预热、重复多次，并报告硬件与版本。

这些命令只说明“结论需要什么证据”，本阶段不要求执行。解读时先绑定 CPU 型号、NUMA 拓扑、Linux 内核、容器配额和工作负载；单个计数器升高不能独立证明根因。
