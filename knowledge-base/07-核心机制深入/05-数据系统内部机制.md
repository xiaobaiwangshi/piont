# 数据系统内部机制

## 统一视角

MySQL、Redis、Elasticsearch、Kafka 都在解决“数据如何写入、组织、复制、恢复和查询”，差别来自主要访问模式与一致性目标。

| 系统 | 主结构 | 主要访问 |
|---|---|---|
| MySQL/InnoDB | B+ 树页 + redo/undo | 事务、点查、范围、关联 |
| Redis | dict/listpack/skiplist 等 | 内存键值与数据结构命令 |
| Elasticsearch/Lucene | 倒排索引 + immutable segment | 全文检索、聚合 |
| Kafka | 分区追加日志 | 顺序写、订阅、重放 |

## WAL 与顺序写

Write-Ahead Logging 的共同思想：先把恢复所需记录追加到日志，再异步整理最终数据结构。顺序追加通常比随机更新更适合存储设备，也便于复制。

- InnoDB redo 支持页修改恢复。
- Elasticsearch translog 保护 refresh 前写入。
- Kafka 分区本身就是追加日志。
- Redis AOF 记录写命令。

它们的日志格式、提交语义和恢复保证不同，不能因为都叫 log 就互换理解。

## InnoDB 页、版本与恢复链

B+ 树页、Buffer Pool、层高公式和日志职责先见 [MySQL](../04-组件/01-MySQL.md)，本节只沿内部状态变化继续推理。

### Buffer Pool 页生命周期

```text
查找页 → Buffer Pool miss → 从表空间读取页 → 加入 LRU
→ 事务修改内存页并先生成 redo → 页进入脏页集合
→ 后台按 checkpoint、脏页比例和淘汰需求刷新
→ 页变干净 → 冷页在需要空间时才可安全淘汰
```

页框数只是容量上限，命中率取决于工作集。上层 B+ 树页、热点叶子页和全表扫描在 LRU 中竞争；一次扫描是否污染热点还与 old/young 分区和读取方式有关。累计命中率很高也可能掩盖短时抖动，应观察时间窗口内物理读、脏页、redo 产生/刷新速度与查询尾延迟。

当脏页产生长期快于刷盘，checkpoint 追不上写入，redo 可复用空间逐渐缩小；InnoDB 会加强刷新，极端时前台写入等待。反过来，为追求“零脏页”过度刷新也会浪费 I/O，优化目标是让写入、恢复时间与存储能力匹配。

### MVCC undo 链与 purge

更新记录时，新版本留在聚簇索引页，旧值通过 undo 形成版本链。一致性读使用 Read View 沿链寻找可见版本；回滚也利用 undo 撤销未提交修改。undo 因而同时服务事务回滚和历史版本读取，但不是永久历史档案。

当旧版本不再被任何活动 Read View 需要时，purge 才能清理相应 undo 和已删除记录。长事务或长时间一致性快照会固定较老的可见边界，造成历史链变长、undo 表空间增长、purge 滞后，并让查询遍历更多版本。处理重点是定位并结束不必要的长事务，而不是直接删除 undo 文件。

### redo、binlog、checkpoint 与 doublewrite

启用 binlog 的事务提交要协调两套日志：InnoDB 把 redo 置于 prepare 状态，Server 层写 binlog，再由 InnoDB commit。恢复时可结合 binlog 是否完整决定 prepared 事务应提交还是回滚，避免“数据已提交但没有复制事件”或相反。group commit 允许多个事务分摊日志同步成本，但持久性仍受刷盘参数、操作系统和存储设备保证影响。

Checkpoint 推进表示更早 redo 对应的脏页已持久化，旧 redo 空间可复用；它管理恢复起点和日志空间。Doublewrite 则在数据页落盘过程中保留完整页副本，处理断电造成的 torn page。前者不负责修复半页，后者也不代替 redo，二者职责不同。

崩溃恢复可按以下证据链理解：先读取 checkpoint 和日志状态；若数据页撕裂，先从 doublewrite 恢复完整页；再用 checkpoint 之后的 redo 重做到一致状态；最后回滚未提交事务并由后台继续 purge。具体阶段、并行度和数据结构随 MySQL 5.7、8.0、8.4 变化，这条链只描述稳定职责。

### 二级索引、回表与写放大

二级索引叶子保存“二级键 + 主键”。非覆盖查询先访问二级叶子，再按主键访问聚簇索引；批量结果可能带来大量离散逻辑读，缓存未命中时才转化为物理随机 I/O。MRR 等优化可以重排部分访问，但不能消除回表本身。

每增加一个二级索引，插入、删除和相关列更新都要维护另一棵 B+ 树，产生额外页修改、redo、Buffer Pool 占用、分裂和备份体积。宽主键还会复制进所有二级索引。索引收益应以真实读路径抵消这些写放大，而不是追求“覆盖所有列”。

### 复制与恢复边界

binlog 复制传播已提交事件，redo 恢复本机 InnoDB 页，备份提供独立恢复基线，三者不能互换。异步复制可能在主库故障时丢失尚未传出的事务；半同步降低部分窗口，但收到日志不代表从库已经执行。GTID 简化事务身份和接续位置，不自动解决延迟、冲突或零丢失。

恢复到目标时间通常是“恢复一致性全量备份 → 应用其后连续 binlog → 在误操作前停止 → 校验 → 切流”。能否满足 RPO/RTO 取决于备份新鲜度、日志连续性、下载和重放速度、密钥与版本兼容，以及是否真正验证过恢复结果。本阶段只整理推理链，不执行恢复实验。

## Redis 的延迟模型

单分片串行执行意味着一条慢命令阻塞后续命令。复杂度必须结合元素数：

- `GET` 通常 O(1)。
- `HGETALL`、`SMEMBERS` 返回量与集合大小相关。
- Lua/Function 执行期间也占用命令线程。

网络 pipeline 降低 RTT，但不会降低命令自身 CPU 复杂度。大 key、fork、AOF fsync 和内存换页都能制造尾延迟。

## Lucene Segment

写入先缓冲，refresh 生成不可变 segment；删除通常先标记，merge 再回收。不可变结构便于并发搜索和缓存，但 merge 会消耗 I/O/CPU，并暂时需要额外磁盘。

倒排表保存 term 到文档列表，BM25 综合词频、逆文档频率和文档长度评分。相关性不是“包含越多越好”，需要用真实查询集评估召回率与排序质量。

segment 不可变减少了并发修改复杂度，但把成本转移到 refresh 与 merge。过短 refresh interval 会制造小 segment；merge 需要同时读取旧段、写新段并保留空间，在磁盘接近水位时风险更高。

## Kafka 分区复制

每分区有 leader 和 follower。生产者写 leader，follower 拉取；ISR 是与 leader 保持足够同步的副本集合。可靠性由 replication factor、`acks`、`min.insync.replicas`、unclean leader election 等共同决定。

分区数决定消费并行度上限和元数据成本。增加分区后 key 到分区映射可能改变，跨时期全局顺序也受影响；不能只为提高吞吐无限加分区。

## 数据同步的正确边界

MySQL → Redis/ES/Kafka 常用路径：

```text
业务事务写 MySQL + outbox
→ CDC/发布器
→ Kafka
→ Redis/Elasticsearch 消费者幂等更新
→ 对账与重建
```

必须定义：事件 ID、实体版本、乱序策略、删除语义、Schema 兼容、重放起点和全量重建流程。

## 容量估算

### MySQL

数据页 + 所有二级索引 + undo/redo/binlog + 临时空间 + 备份。索引不是免费副本，每个索引都会增加写放大。

### Redis

抽样 `MEMORY USAGE`，再加碎片、复制/AOF、客户端缓冲和 fork COW 余量。

### Elasticsearch

原始 JSON、倒排、doc values、stored fields、segment 合并余量和副本。磁盘水位前必须有恢复空间。

### Kafka

```text
磁盘 ≈ 日写入量 × 保留天数 × 副本数 × 格式开销
```

再预留重分配、峰值和操作系统页缓存。Kafka 性能高度依赖页缓存，不应把机器内存只看成 JVM heap。

## 选型问题

先问：权威数据是谁、查询模式是什么、延迟/一致性要求、是否需要重放、数据能否重建、团队能否运维。若 MySQL 索引已满足搜索，不必增加 ES；若 Redis Stream 足够，不必因“架构先进”上 Kafka。
