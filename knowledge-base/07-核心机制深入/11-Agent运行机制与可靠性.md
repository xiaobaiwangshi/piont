# Agent 运行机制与可靠性

## 阅读边界

架构模式见[Agent 架构、编排与多 Agent](../09-AI与大模型/05-Agent架构编排与多Agent.md)。本章深入状态、事件、恢复、一致性、上下文预算和并发数量级；不重复 Transformer 公式，也不绑定框架 API。

## 状态、事件与派生视图

Agent 的可靠核心不是聊天记录，而是可验证的运行状态：

```text
command（想做什么）
→ event（已经发生什么，不可变）
→ state（由事件归约出的当前状态）
→ effect（对外部系统的动作）
```

事件至少记录 task/step ID、序号、类型、输入摘要、输出引用、时间、版本和 trace ID。大对象存 artifact 存储，事件只保存内容哈希/URI/权限，避免事件表变成无限对话 Blob。

状态快照加事件增量可减少回放时间。快照必须标记覆盖到的 event sequence；恢复时读取快照后应用更高序号事件。事件 Schema 升级要有兼容读取或迁移策略。

## Checkpoint 与 Replay

安全恢复点满足：节点输入已固定、此前结果已持久化、是否执行过副作用可查询。恢复流程：

1. 获取 task 租约或乐观锁，防止两个 worker 同时恢复。
2. 加载 checkpoint 和之后的事件。
3. 检查等待中的工具调用/审批真实状态。
4. 对已确认完成的 step 复用结果；对状态未知的副作用先查询。
5. 从允许的下一条边继续，并记录恢复原因。

Replay 可用于调试，但外部工具不能随意重放。离线评测应 mock/freeze 工具结果；生产恢复应引用原 tool call 或按幂等语义执行。

## At-Least-Once 是常态

网络和进程故障下，很难让 Agent、队列、数据库与第三方 API 共同实现端到端 exactly-once。工程上通常接受消息/工具至少一次投递，再把业务效果做成幂等。

```text
idempotency_key = tenant + business_action + resource + logical_step
```

工具执行端持久化 key、请求摘要、状态和结果。相同 key + 相同请求返回原结果；相同 key + 不同请求应冲突报错。只在客户端“记住调用过”不能覆盖超时和重启。

## 状态未知、事务间隙与补偿

典型失败窗口：

```text
外部付款成功 → 响应丢失 → Agent 记录失败 → 重试付款
```

正确顺序是用服务端幂等键提交；超时后调用查询接口确认。若外部系统不支持幂等，使用本地 intent/执行记录、业务唯一约束和人工处理状态未知结果。

Saga 补偿不是数据库回滚。取消订单、退款、撤销消息可能失败或只能部分恢复，因此补偿也是可重试、有审计、可人工接管的业务动作。

## 上下文是有损工作集

上下文由系统指令、用户输入、检索证据、工具结果、历史摘要和输出预算竞争：

```text
usable_context = model_limit
                 - reserved_output
                 - fixed_instructions
                 - tool_schemas
                 - safety_margin
```

剩余空间才分给当前任务。不能把模型声明的最大窗口全部塞满：token 估算存在分词差异，工具调用和回复还需空间，长上下文也可能降低有效注意。

优先级通常是：不可变约束/身份权限 → 当前目标和状态 → 必需证据 → 最近相关事件 → 摘要。原始日志和低相关历史保存在外部存储，需要时检索。

## 摘要损失与记忆漂移

摘要会丢失否定、数字、来源和未解决分歧。不要让摘要成为唯一事实源：

- 结构化状态保存 ID、金额、时间、状态和约束。
- 摘要引用原事件/artifact，可回溯原文。
- 新摘要基于权威状态和必要原文，不只递归总结旧摘要。
- 长期记忆有来源、置信度、有效期、租户/用户 ACL 和删除路径。

“用户喜欢简洁”可作为偏好记忆；“订单已退款”必须查询业务系统。

## 多 Agent 的循环与活性

- deadlock：A 等 B，B 又等 A，双方永不推进。
- livelock：双方不断交换/重规划，但状态没有有效变化。
- cycle：任务图出现未受控回边或循环委派。
- duplicate ownership：多个 worker 都认为自己负责同一动作。

检测指标包括无状态进展轮数、相同任务/参数重复次数、等待依赖图和租约超时。控制措施是 DAG/最大回边次数、唯一 owner、全局 step ID、委派深度、心跳/租约和强制终止。

## Trace：把证据串起来

一次 Agent task 的 trace 至少关联：

```text
request → prompt/context version → retrieval query/results
→ model request/response → selected action → tool call/result
→ state transition/checkpoint → validation → final output
```

记录 token、延迟、重试、费用、模型/工具版本和输入输出摘要；敏感正文脱敏或只保存受控引用。trace 能解释“为什么走到这里”，但不是无限保存所有隐私数据的理由。

## 并发与 Little's Law

稳定系统中可用 Little's Law 粗估在途量：

```text
L = λW
```

若平均每秒到达 5 个任务，平均端到端停留 20 秒，则平均约有 100 个在途任务。这不是需要 100 个 CPU 线程：许多任务在等待模型、工具或人工；应采用异步状态和有界 worker。

容量还受模型 API 并发/RPM/TPM、工具连接池、队列积压和租户配额限制。高并发下必须做 admission control 和 backpressure，不能无限创建 Agent 循环。

## 步骤成功率与长链路

若粗略假设 n 个必要步骤独立且每步成功率为 p，则一次全链成功率约：

```text
P(success) = p^n
```

例如 10 步、每步 98%，全链约 `0.98^10 ≈ 81.7%`。真实步骤并不独立，但这个数量级说明：缩短链路、确定性校验、可恢复 checkpoint 和局部重试比盲目增加 Agent 步骤重要。

## 不变量

生产实现应明确并测试以下不变量：

- 同一 logical step 的副作用至多产生一个业务结果。
- 终态不能自行回到 running；恢复必须通过明确命令和新事件。
- 未批准的高风险动作不能进入 executing。
- 每个状态转换都能追溯到事件、版本和执行者。
- 预算为零或取消后不能再发起新模型/工具调用。
- 任务只属于一个租户，检索、记忆和工具不能跨租户。

## 自测答案

1. **为什么不承诺端到端 exactly-once？** 多系统间存在网络和崩溃窗口，通常以至少一次投递加业务幂等实现可靠效果。
2. **checkpoint 后怎样恢复副作用？** 查询原调用/幂等键状态，不能把超时等同未执行。
3. **摘要为何不能当权威数据？** 它是有损压缩，可能丢数字、否定、来源和更新。
4. **Little's Law 用来做什么？** 根据到达率和停留时间估算平均在途量，帮助规划队列与并发。
5. **如何识别 livelock？** 动作持续发生但业务状态或信息增量长期为零。
6. **长链为何脆弱？** 多个必要步骤的失败概率累积，还增加外部状态变化和重试窗口。

版本边界：事件日志、幂等、租约、状态机和 Little's Law 是稳定工程原理；框架 checkpoint、memory 和 replay 的精确语义必须结合存储实现及目标版本验证。
