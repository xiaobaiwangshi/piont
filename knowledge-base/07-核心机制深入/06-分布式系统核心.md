# 分布式系统核心

## 分布式系统为什么难

网络会延迟、丢包、重复、乱序和分区；进程会暂停和崩溃；时钟不完全同步。调用超时只表示“调用方没及时收到结果”，不能证明对方没有执行。

## 时间与顺序

- 物理时钟可由 NTP 校准，但仍会漂移/回拨。
- 单调时钟适合计算持续时间。
- Lamport clock 表达 happens-before 的部分顺序，不代表真实时间。
- 版本号/offset 常比 wall clock 更适合冲突判断。

依赖毫秒时间戳生成唯一 ID 可能碰撞；依赖客户端时间判断最后写入也可能被时钟偏差破坏。

## 复制模式

- 单主：写入简单，主故障需选举，可能复制延迟。
- 多主：多地写入，必须解决冲突。
- 无主/quorum：客户端向多个副本读写，需处理 read repair、hinted handoff 等。

同步复制提高确认强度但增加延迟和可用性成本；异步复制响应快但故障时可能丢已确认数据。

## 共识

Raft/Paxos 类共识让节点在故障和消息延迟下对日志顺序达成一致。核心包含 leader、term/ballot、quorum 和日志复制。

多数派不是“数据永远不丢”的简单开关：磁盘持久性、成员变更、快照、错误实现和运维操作仍影响结果。Redis Sentinel 主从故障转移也不等同于共识复制的数据保证。

## 幂等与去重

写 API 使用业务幂等键：

```text
UNIQUE(tenant_id, idempotency_key)
```

首次请求在事务内写入业务结果和幂等记录；重复请求返回已有结果。只在 Redis `SETNX` 短暂去重可能因过期、故障转移或数据库提交窗口失效，数据库约束是常见最终防线。

消息消费者用 event_id 或实体版本幂等。去重记录也需生命周期；永久保存所有 ID 会无限增长。

## 分布式事务

- 2PC/XA：协调多个资源准备与提交，强语义但阻塞、运维复杂。
- Saga：一组本地事务与补偿，适合长业务流程，但补偿不总能恢复现实世界。
- Outbox：业务状态和待发事件同库事务，解决数据库与消息双写。
- TCC：Try/Confirm/Cancel，要求业务预留和补偿接口。

先缩小强一致边界，再选择协议；不要把“最终一致性”当作无需处理失败。

## 超时、重试与熔断

调用链 A→B→C 若每层重试 3 次，最坏可把一次请求放大为多次下游调用。设计重试预算：只在少数层重试、有限次数、指数退避、抖动、总 deadline 和幂等。

熔断器状态常为 closed/open/half-open。半开只放少量探测，成功恢复，失败重新打开。限流保护自己，熔断保护对故障依赖的调用资源。

## 一致性哈希与分片

一致性哈希把节点和 key 映射到环，虚拟节点改善分布；节点变化只迁移邻近区间。固定槽位（Redis Cluster）把 key→slot 与 slot→node 分开，更便于迁移治理。

无论哪种分片都要处理热点、扩容搬迁、跨分片查询、全局唯一、事务和再均衡。

## 限流算法

- 固定窗口：简单，窗口边界会突刺。
- 滑动窗口：更平滑，状态成本高。
- 漏桶：固定流出速率，适合整形。
- 令牌桶：允许一定突发，长期速率受控。

令牌桶参数：速率 r、桶容量 b。持续流量平均不超过 r，短时间可突发最多 b。分布式限流需决定一致性要求；全局强一致计数可能自己成为瓶颈。

## 故障模型与演练

设计时明确考虑：进程崩溃、机器断电、磁盘损坏、网络分区、延迟飙升、重复消息、时钟偏差、配置错误和人为误操作。用故障注入验证超时、选举、降级和恢复，而不是只画“正常流程”架构图。
