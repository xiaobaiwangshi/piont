# 协议栈与网络性能

本章解释 Linux 实现与容量边界，不重复定义协议语义和窗口公式。滑动窗口、慢启动、BDP、DNS、TLS 与 HTTP 的完整学习顺序见[计算机网络](../01-基础/02-计算机网络.md)。命令仅用于说明证据来源，本阶段不要求实际执行。

## Linux 主机收发包路径

发送路径可概括为：

```text
应用 write/send
→ socket 发送缓冲
→ TCP/UDP
→ IP 路由与 netfilter/conntrack
→ qdisc 排队
→ 网卡驱动描述符
→ DMA 读取内存
→ 网卡发到链路
```

接收方向大致相反：网卡把 frame DMA 到接收环 → 中断通知或 NAPI 轮询 → 驱动构造内核包结构 → Ethernet/IP/TCP/UDP 处理 → netfilter/conntrack → socket 接收缓冲 → 唤醒等待应用。

路径中的任一点都可能成为瓶颈：应用供数、socket 缓冲、软中断 CPU、qdisc、网卡 ring、链路丢包或接收端读取。CPU 高也可能来自小包率、软中断和协议处理，而不是业务函数。

## 五类容易混淆的容量上限

| 资源 | 限制什么 | 满载时常见现象 |
|---|---|---|
| SYN backlog | 尚未完成握手的连接 | SYN 丢弃、重传、握手超时 |
| accept queue | 已握手但应用尚未 accept 的连接 | 连接建立异常或排队，取决于实现 |
| socket send/receive buffer | 单连接可缓冲的字节 | 应用阻塞/EAGAIN、零窗口、吞吐受限 |
| file descriptor | 进程能引用的 socket/文件 | `EMFILE`/`ENFILE`、accept/open 失败 |
| conntrack/临时端口 | NAT/有状态连接和本地新建连接 | 新连接失败、映射冲突或丢包 |

`somaxconn`、应用 `listen(backlog)`、TCP SYN 参数、fd 限制和 conntrack 表不能用一个“最大连接数”相互替代。代理请求还可能同时占客户端与上游两个连接。

## 同网段如何找到目标

主机对目标 IP 和本机 IP 分别应用子网掩码。若同网段，通过 ARP（IPv4）或 Neighbor Discovery（IPv6）解析链路层地址，再封装 Ethernet frame；若不同网段，解析默认网关的链路地址，把 IP 包交给网关。

交换机依据 MAC 表转发帧，路由器依据 IP 路由表转发包。MAC 地址只负责当前链路，不会一路用于互联网端到端寻址。

## NAT 与连接跟踪

家庭/云网关常将私网源 IP:port 映射为公网 IP:port，并维护连接跟踪表。NAT 会改变端点可见地址，影响：

- 服务器看到的源 IP 可能是代理/NAT。
- 大量客户端共享一个出口，`ip_hash` 分布可能失衡。
- 出口临时端口耗尽会导致新连接失败。
- 长连接需要 keepalive 和空闲超时配合。

conntrack 为有状态防火墙/NAT 保存五元组和状态，容量与超时会影响新连接。大量客户端共用一个出口时，公网地址与临时端口组合也有限；增加应用 worker 不会扩大出口端口空间。

## MTU、MSS 与分片

MTU 限制单个链路层载荷，TCP MSS 通常是路径 MTU 扣除 IP/TCP 首部后的单段数据上限。IPv4 中间路由器可能分片，IPv6 中间路由器不分片；现代传输通常依赖 Path MTU Discovery 避免分片。

错误丢弃 ICMP “Packet Too Big/Fragmentation Needed” 可能形成 PMTU 黑洞：小包成功，大响应或 TLS 握手卡住。排查时比较不同负载大小、抓 ICMP、检查隧道额外开销，不要把 MTU 固定改小后就结束定位。

## TCP 状态机

常见主动打开路径：

```text
CLOSED → SYN-SENT → ESTABLISHED
```

主动关闭方常进入：

```text
ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED
```

TIME_WAIT 让迟到报文过期，并允许重发最终 ACK。大量 TIME_WAIT 不等于故障；应检查是否短连接过多、连接复用不足、端口范围和是否由正确一方主动关闭。不要用危险内核参数粗暴消除协议保护。

半关闭允许一个方向发送 FIN 后继续接收另一个方向的数据。RST 则是异常终止，不保证未读数据被应用处理。排查“连接被关闭”必须区分 FIN、RST、超时与代理主动取消。

## TCP 性能的四个边界

1. 接收端：`rwnd`。
2. 网络拥塞：`cwnd`。
3. 应用：是否持续读写 socket。
4. 系统：socket buffer、队列、CPU 和丢包。

有效在途数据约受 `min(rwnd, cwnd)` 限制。吞吐上限还可用 `window/RTT` 粗估。滑动窗口、慢启动和 BDP 的计算见[计算机网络](../01-基础/02-计算机网络.md)。

### 丢包为什么代价大

丢包不只是重发一段：它可能降低拥塞窗口、触发队头等待、增加 RTO，并让上层超时重试进一步放大流量。高 RTT 链路恢复窗口更慢。

## 网卡与协议栈 Offload

- checksum offload：由网卡计算/验证部分校验和。
- TSO/GSO：内核交给网卡或更低层分段，减少每段处理成本。
- GRO/LRO：接收方向合并多个包后再交给上层，降低包处理开销。

因此在发送主机抓包可能看到“超大 TCP segment”或未完成校验和，这不一定是线上真实帧；分段/校验可能在抓包点之后完成。分析包大小和 checksum 前要记录抓包位置与 offload 状态。

## DNS 深入

- Stub resolver：应用/系统的轻量解析入口。
- Recursive resolver：替客户端完成层级查询并缓存。
- Authoritative server：提供域名权威记录。
- TTL：缓存有效时间，不等于变更会在全球精确同时生效。
- Negative caching：不存在结果也可能被缓存。

DNS 轮询不感知实时实例健康，适合粗粒度流量分配；应用层负载均衡负责更快健康检查和路由。

## TLS 1.3 简化过程

```text
ClientHello：版本、套件、key share、随机数、SNI/ALPN
→ ServerHello：选择参数与 key share
→ 双方计算握手密钥
→ 服务端发送加密参数、证书与签名
→ 客户端验证域名、证书链、有效期与签名
→ Finished 验证握手完整性
→ 应用数据密钥传输 HTTP
```

证书证明公钥与域名身份关系；它不直接“加密整个大文件”。会话票据可支持恢复，0-RTT 有重放风险，只适合可安全重放的请求。

## HTTP/1.1、HTTP/2、HTTP/3

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输 | TCP | TCP | QUIC/UDP |
| 多路复用 | 需多连接/管线受限 | 单连接多流 | 单连接多流 |
| 头压缩 | 无标准动态压缩 | HPACK | QPACK |
| 丢包影响 | 当前 TCP 连接 | 所有流受 TCP 队头阻塞 | 主要影响相关 QUIC 流 |
| TLS | 可选 | 浏览器实际常用 TLS | 内建 TLS 1.3 |

HTTP/2 多路复用减少应用层队头阻塞，但底层 TCP 丢包仍影响同连接全部流。HTTP/3 把可靠性做到独立 QUIC 流，迁移和握手也更灵活，但 UDP 路径、CPU 和运维支持需要实测。

## 代理、缓冲与流式响应

反向代理可能缓冲请求和响应：

- 普通 API 缓冲能提高上下游解耦和吞吐。
- SSE/AI 流式输出需要关闭或调整响应缓冲，及时 flush。
- 大上传可先落临时文件，保护上游，但增加磁盘和首包延迟。

“应用已经流式写出”不等于客户端立刻收到，需检查应用缓冲、FastCGI/HTTP 代理缓冲、压缩、CDN 和客户端读取。

## 网络排查思路与命令示例

```bash
dig +trace example.com
ip route get 203.0.113.10
ss -ti dst 203.0.113.10
curl -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' -o /dev/null -sS https://example.com/
openssl s_client -connect example.com:443 -servername example.com -alpn h2
```

分段时间能判断慢在 DNS、TCP、TLS、服务首字节还是下载。一次测量不足以下结论，应从客户端和服务端同时取证。

分析时可设想用不同 RTT、丢包、重排和响应大小验证假设，并观察 `ss -ti` 中 RTT、`cwnd`、重传与吞吐变化。若以后实际验证，必须在隔离环境中进行并记录内核、拥塞算法和网络条件。

来源线索见 [`raw_doc_` 原始资料主题索引](../99-原始资料主题索引.md)中的《计算机网络》，TCP、TLS、HTTP 与 QUIC 的最终语义以现行 RFC 为准。

## 协议保证与实现细节的边界

RFC 定义报文、状态和互操作语义；Linux 决定队列结构、自动调优、拥塞算法、offload、观测字段与性能策略。诸如初始窗口、buffer 上限、backlog 行为、CUBIC/BBR 版本和 `ss` 输出都属于实现相关内容，不能作为所有操作系统的固定结论。
