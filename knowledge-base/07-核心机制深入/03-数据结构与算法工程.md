# 数据结构与算法工程化

基础结构、算法选择、复杂度定义和 Bloom/Top K/外部排序算例先见[数据结构与算法](../01-基础/04-数据结构与算法.md)。本章只解释正确性、不变量、摊还与误差来源，以及内存、并发和外部存储如何改变成本；本阶段不运行代码、测试或 benchmark。

## 从不变量开始

数据结构的正确性依赖不变量：

- 栈：只从同一端入栈/出栈。
- 二叉搜索树：左子树键小于当前键，右子树大于当前键（重复键规则另定）。
- 堆：父节点不大于/不小于子节点。
- 并查集：父指针最终指向集合代表。

实现和调试时先写不变量，再检查每个操作是否保持它，比记代码模板更可靠。

每个操作的证明可拆成三步：前置条件成立；操作的每个分支保持不变量；结束后不变量与返回值共同推出后置条件。边界错误通常来自空结构、首尾节点、重复键、整数溢出或状态更新顺序。

循环不变量还要证明：初始化前成立；每轮执行后仍成立；循环终止时能推出目标结论。二分查找的“目标仍在候选区间”、归并的“输出前缀已经有序且元素守恒”、Dijkstra 的“已确定集合距离不再改进”都是这种思路，但成立前提不同。

样例只能发现错误，不能代替一般证明。寻找反例时优先缩小到最少元素、最短环、最小权值组合或第一个越界位置，让破坏不变量的步骤可见。

## 动态数组的摊还分析

容量从 1 开始按 2 倍增长，连续追加 n 个元素时，发生的历史搬迁量构成 `1+2+4+...`，小于 `2n`；加上 n 次新元素写入，总工作仍为 `O(n)`，所以单次追加摊还 `O(1)`。这不掩盖某次扩容需要线性搬迁和额外峰值内存。

增长因子小会更频繁搬迁，因子大则增加未使用容量。缩容若在“刚低于满载”就发生，可能与扩容来回抖动；工程实现通常设置不同扩/缩阈值或不主动缩容。摊还证明必须把这些策略写进前提。

## 哈希表深入

哈希表平均查找 `O(1)` 依赖：哈希分布、装载因子和扩容策略。

- 链地址法：冲突元素放桶内链表/数组/树。
- 开放寻址：在线性表内探测空位，如线性、二次、Robin Hood。
- 扩容：申请更大表并重新分布；一次扩容可能 `O(n)`，摊还后插入平均仍可近似 `O(1)`。

攻击者可构造冲突键导致退化，面向不可信输入的运行时会使用随机种子或树化等防护。

### 摊还成本为什么接近常数

以容量倍增为例，可用记账法让每次普通插入额外“支付”少量信用，累积信用覆盖未来搬迁；也可定义与剩余容量相关的势能，扩容的实际成本由势能下降抵消。两种方法都证明一串操作的总成本是 `O(n)`，不表示扩容那一次是 `O(1)`。

哈希表还要把再散列、冲突探测和删除标记计入模型。开放寻址在装载因子接近 1 时探测长度急剧增加；链地址法的桶内长度依赖哈希分布。增量 rehash 可把搬迁分散到多次操作，但会让查询同时检查新旧表，改变常数和并发协议。

## 树结构的选择

| 结构 | 平衡/特点 | 典型场景 |
|---|---|---|
| BST | 可能退化为链表 | 教学/受控输入 |
| AVL | 高度严格平衡、查询稳定 | 读多内存索引 |
| 红黑树 | 平衡约束较松、更新高效 | 有序 map/set、调度 |
| B/B+ 树 | 高扇出，减少外存 I/O | 数据库/文件系统 |
| Trie | 按字符/位共享前缀 | 自动补全、路由 |
| Segment Tree | 区间聚合和更新 | 动态区间查询 |
| Fenwick Tree | 前缀和，结构更小 | 可加减区间统计 |

B 树与 B+ 树不是“B-树/B减树”。B-tree 的 B 不是 Binary；B+ 树把数据集中于叶子，内部节点用于导航。

## 图算法如何选

- 无权最短路：BFS。
- 非负权单源最短路：Dijkstra。
- 含负权边：Bellman-Ford；负环时最短路无定义。
- 全源最短路：小规模可用 Floyd-Warshall；稀疏图可多次单源算法。
- 最小生成树：Kruskal 或 Prim，解决连通成本，不解决有向最短路径。
- DAG 依赖：拓扑排序；有环说明依赖冲突。

算法选择前确认有向/无向、权值范围、稠密度、是否动态更新和输出需求。

## 动态规划不是背公式

以 0/1 背包为例，`dp[w]` 表示容量 w 下最大价值：

```text
dp[w] = max(dp[w], dp[w-weight[i]] + value[i])
```

一维压缩时容量必须从大到小遍历，防止同一物品在本轮重复使用；完全背包反向从小到大。这一遍历方向来自状态依赖，不是记忆口诀。

DP 设计检查：状态是否足够描述未来、转移是否遗漏、初始化是否把不可达状态当 0、遍历顺序是否覆盖依赖。

空间压缩会覆盖旧状态，必须用依赖方向证明覆盖后不会读取本轮新值。0/1 背包倒序和完全背包正序的差异正来自“同一物品能否重复使用”，不是可互换的代码风格。

## 随机与概率结构

- Bloom Filter：节省空间、允许假阳性、不支持普通精确删除。
- Count-Min Sketch：近似频率，可能高估。
- HyperLogLog：近似基数统计。
- Reservoir Sampling：未知总量的数据流中等概率抽样。

概率结构必须把误差率写入需求。例如 Bloom Filter 位数与哈希函数数量由元素数和目标误判率共同决定，不能只说“用 bitmap 防穿透”。

### Bloom Filter 的误差来源

主章节给出了 m、n、目标假阳性率 p 和哈希次数 k 的容量公式。直觉上，插入越多或 bit 数越少，置 1 比例越高；查询的 k 个位置全为 1 的概率随之上升。实际误差还受哈希相关性、容量超标、并发写和序列化兼容影响，因此上线容量必须保留增长余量。

- Count-Min Sketch 的多个计数器取最小值，因此碰撞只会使估计偏高；误差与宽度、深度和置信度参数相关。
- HyperLogLog 根据哈希前导零等统计估算基数，误差是统计量而非单次确定偏差；小基数和合并实现需看版本。
- Reservoir Sampling 在不知道总量时维持固定大小样本；第 i 个元素按适当概率进入并随机替换，保证最终每个元素等概率入样。

概率结构节省空间的代价是误差模型。若业务不能接受假阳性、近似计数或抽样误差，应使用精确结构，而不是事后把概率结果当事实。

## 并发数据结构

线程安全不等于加一把全局锁：

- 粗粒度锁：实现简单，吞吐上限低。
- 分段锁/sharding：不同分片并行。
- Copy-on-write：读多写少。
- 原子/CAS：适合简单状态机，需理解 ABA、内存顺序和重试成本。
- 消息传递：把可变状态交给单一所有者。

先用锁做正确，再通过 profile 证明竞争后优化；无锁结构的验证成本很高。

### CAS、ABA 与安全回收

CAS 只在内存值仍等于预期时更新，可构造重试循环，但竞争激烈时会反复失败并消耗 CPU。ABA 表示值从 A 变 B 又回 A，单看位模式的 CAS 无法发现中间变化；版本标记能解决部分场景，但存在位宽和回绕边界。

另一个难点是对象生命周期：线程读取指针后，其他线程可能删除并释放对象。hazard pointer、epoch/RCU 等方案推迟回收直到确认没有读者，各自牺牲内存、延迟或实现复杂度。垃圾回收语言也不自动解决逻辑 ABA 和复合状态原子性。

所有权分片和消息传递经常比共享无锁结构更容易证明。只有锁竞争被证明确为瓶颈，并且团队能维护内存顺序与回收协议时，才值得引入更复杂方案。

## 外部排序与大数据

数据大于内存时：

1. 分块读入内存排序并写临时有序文件。
2. 使用最小堆做 k 路归并。
3. 流式写结果。

复杂度之外还要考虑磁盘顺序 I/O、临时空间、文件数、归并路数和失败恢复。

### 失败与恢复边界

生成初始段时可先写带唯一标识的临时文件，完整落盘后再登记为可归并输入；归并输出同样先写临时结果，校验完成后原子切换清单。崩溃恢复依据清单区分完整段、未完成输出与可安全清理文件，避免只凭文件名猜测。

归并路数不是越大越好：每一路需要输入缓冲和 fd，路数增加可减少轮数，但会压缩单路缓冲、增加随机性和打开文件压力。实际计划要同时满足内存、fd、临时空间、带宽和恢复时间。

### 页访问成本模型

对页式存储，比较次数不是唯一成本。若内部节点扇出为 `F`、叶子页数量为 `L`，树高可粗估为：

```text
height ≈ 1 + ceil(log_F(L))
```

根页和上层页常驻缓存时，一次查询的真实物理 I/O 可能少于树高；缓存未命中、随机读、范围扫描和二级索引回表会改变成本。具体 B+ 树页容量与算例见 [MySQL](../04-组件/01-MySQL.md)。

## 非执行的评估方法

以下方法用于说明知识结论需要怎样验证，本阶段不实际编写或运行测试、性质检查和 benchmark。

### 边界集

- 空输入、单元素。
- 已排序、逆序、全重复。
- 最大/最小值和整数溢出。
- 图不连通、含环、自环、重边。
- Unicode、空字节和异常输入。

### 性质测试

排序结果应同时满足“单调有序”和“元素多重集合不变”。相比只写几个固定输出，性质测试配合随机输入更容易发现边界问题。

### 性能评估口径

报告数据规模、分布、预热、重复次数、硬件和内存分配。不要用一个小数组证明某算法在生产更快；小数据常由常数和缓存主导。

复杂度负责预测增长趋势，benchmark 只测给定实现和环境。评估时应分别记录墙上时间、CPU 时间、峰值内存、分配量、缓存/I/O 特征和输出正确性；如果数据分布不同，平均性能结论不能直接外推。
