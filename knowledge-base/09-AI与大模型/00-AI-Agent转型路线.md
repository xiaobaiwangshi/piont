# AI Agent 转型路线

## 定位

目标不是从十年全栈开发“清零转行”，而是把已有的 Web、数据库、队列、分布式系统、网络、可观测性与安全能力迁移到 Agent 系统，并补齐大模型的概率性、上下文、检索、工具调用和评测方法。

最终应能设计和评审这样的系统：

```text
用户/API
→ Agent 状态机/工作流
→ LLM 决策或结构化输出
→ RAG/记忆/工具/人工节点
→ 持久化、事件、审计
→ 评测、可观测性、安全和成本控制
```

本阶段只整理知识、计算和案例，不下载模型，不搭建向量库、Agent 框架或 GPU 推理实验。

## 已有能力如何迁移

| 全栈能力 | Agent 工程中的对应问题 |
|---|---|
| HTTP/API/SSE | 模型网关、流式 token、取消、工具 API、Webhook |
| MySQL | 会话、任务、step、幂等键、审计、评测结果 |
| Redis | 短期状态、限流、锁、缓存；不是默认长期记忆真相源 |
| Elasticsearch | BM25、混合检索、metadata 过滤与向量检索 |
| Kafka/队列 | 长任务、异步工具、事件工作流、重试与死信 |
| 分布式系统 | 超时、幂等、补偿、状态恢复、并发修改 |
| 安全 | 最小权限、租户隔离、密钥、审批、审计、注入防御 |
| 可观测性 | prompt/model/tool/retrieval trace、SLO、成本归因 |

新增难点是：模型输出不是确定性函数；自然语言不是类型安全接口；上下文有限；外部文本可能注入指令；“看起来正确”不能代替评测；工具调用会产生真实副作用。

## 建议的转型产出

学习资料应最终支持四类作品的设计说明，但本阶段不实际搭建：

1. 企业知识助手：权限检索、引用、更新与评测。
2. 工单 Agent：分类、检索、工具执行、人工审批和状态恢复。
3. 代码/运维助手：只读诊断、危险操作确认、沙箱与审计。
4. 多步骤业务办理：确定性 workflow 包裹有限的模型决策节点。

每个作品都要回答：为什么需要模型、为什么需要 Agent、哪些步骤必须确定、事实存在哪里、副作用如何幂等、失败如何恢复、质量怎样回归、安全由谁保证。

## 不走的弯路

- 不从训练 7B/70B 模型开始；先学会可靠使用模型。
- 不把所有历史消息塞进 prompt 当长期记忆。
- 不把 LangChain、LangGraph、AutoGen 等框架 API 当成 Agent 原理。
- 不为展示多 Agent 而制造角色；一个状态机能解决就不要增加通信。
- 不用“回答看起来不错”验收；建立数据集、指标和失败分类。
- 不让模型绕过应用权限直接执行 SQL、shell 或外部写操作。
