# LLM 应用基础与模型接口

## 学习目标

本章把模型视为一个昂贵、概率性、受限流且输出不可信的远程依赖。完成后应能设计消息、上下文、结构化输出、流式调用、错误处理、成本和供应商边界。

模型内部原理见[大模型基础](01-AI与大模型基础Transformer.md)，Agent 编排见[Agent 架构](05-Agent架构编排与多Agent.md)。示例不连接真实模型 API。

## 一次模型调用

```text
业务输入
→ 权限/数据分类
→ 组装固定指令、用户输入、历史、检索和工具结果
→ 模型请求
→ 文本或结构化/工具输出
→ Schema + 业务规则 + 权限校验
→ 展示、重试或执行下一步
```

模型 API 不是数据库事务。超时后服务端可能已完成生成并计费；重试可能产生不同输出；流式连接断开也不说明服务端一定取消。

## 消息与指令层次

不同平台的消息角色和优先级以当前 API 为准，通用概念是：

- 平台/应用固定指令：定义角色、禁止事项、输出协议和工具边界。
- 用户消息：任务目标与数据，不能覆盖应用权限。
- assistant 历史：先前输出，不一定是真实事实。
- tool 结果：外部系统返回的不可信数据，不应被当作高优先级指令。

应把“指令”和“数据”分区，用明确标记说明引用材料仅供回答。提示词不能替代权限检查；即使模型声称拒绝，也要在应用层阻断危险工具。

## Prompt 与上下文工程

一个可维护 prompt 至少包含：

1. 任务和成功条件。
2. 可用事实、禁止假设和缺失信息处理。
3. 输出 Schema/格式。
4. 工具使用规则和停止条件。
5. 少量覆盖关键边界的示例。

few-shot 示例能塑造格式与决策边界，但会占 token、可能过拟合示例或泄露敏感数据。上下文排序会影响注意力：高优先级规则、当前任务和最相关事实应清晰、去重；不要依赖模型从长噪声中自动找出唯一有效句子。

## 结构化输出

需要程序消费时优先使用平台支持的 structured output/JSON Schema，而不是用正则从自由文本猜 JSON。仍需两层校验：

```text
语法/Schema 校验
→ 业务校验（ID 是否存在、金额范围、状态是否允许）
→ 权限与副作用确认
```

模型可能输出合法 JSON 但业务错误，例如不存在的 `employee_id`、越权的 `tenant_id` 或危险的 `action`。枚举、长度、数值范围和附加字段限制越明确，修复成本越低。

修复策略按风险选择：无副作用的格式错误可带错误信息重试；涉及写操作不得自动把未知字段“猜对”，应拒绝或请求用户确认。

## 流式响应

SSE 适合服务端单向 token/事件流：

```text
request accepted
→ metadata/event id
→ text deltas
→ tool/status events（若有）
→ completed | failed | cancelled
```

前端应区分临时文本与最终结果。服务端处理客户端断开、上游取消、代理缓冲、心跳、超时和部分计费。流式展示降低感知等待，不缩短模型实际生成时间；若中途内容需要安全审核，逐 token 展示会增加撤回难度。

## 超时、重试和限流

- 连接超时、首 token 超时、整体超时和空闲 token 超时含义不同。
- 429/限流通常需读取服务端建议并指数退避加抖动。
- 5xx/网络错误是否重试要看请求是否幂等、是否已产生工具副作用。
- 内容拒绝、Schema 长期不满足、上下文过长通常不是盲重试能解决。
- 设置最大尝试次数、总时限和 token/费用预算。

模型调用本身通常无业务写副作用，但 Agent 周边工具有。重试整个 Agent 轨迹前必须有 tool-call 幂等键和已完成 step 记录。

## 模型选择与回退

按任务选择，而不是全局固定“最强模型”：

| 任务 | 关注指标 |
|---|---|
| 分类/路由 | 准确率、结构化稳定、延迟、成本 |
| 抽取 | 字段完整、幻觉率、长文档能力 |
| RAG 回答 | 引用、faithfulness、上下文利用 |
| 工具规划 | 工具选择、参数正确、停止能力 |
| 代码任务 | 可执行正确性、安全、上下文 |

fallback 可能改变 tokenization、Schema、工具能力和安全行为。回退模型必须单独通过回归集，不能只在主模型失败时临时替换。

供应商抽象应统一业务请求、错误、指标和 trace，但不要假装所有 API 特性完全等价。只抽象实际需要替换的能力。

## Token、成本与容量估算

一次调用近似成本：

```text
cost = input_tokens × input_price
     + output_tokens × output_price
     + cache/retrieval/tool/infra cost
```

假设输入 6000 token、输出 800 token，输入每百万 token 2 元、输出每百万 8 元：

```text
0.006×2 + 0.0008×8 = 0.0184 元/次
```

每天 10 万次约 1840 元/天，尚未计重试、RAG、工具和日志。价格必须绑定供应商、模型和日期。

上下文预算示例（最大 16k）：固定指令 1k、历史摘要 2k、检索 8k、用户输入 1k、预留输出 2k，还剩 2k 安全余量。不能把全部 16k 给输入，否则可能没有输出空间或触发截断。

## 可观测性

每次请求至少关联：request/trace ID、租户、模型与版本、prompt 版本、输入/输出 token、TTFT、总延迟、停止原因、错误类型、重试、费用，以及关联的 retrieval/tool/Agent step。

生产日志避免默认记录完整 prompt、用户隐私和密钥。可保存哈希、脱敏摘要或受控采样，并设置访问权限和保留期。

## 常见失败证据链

| 现象 | 先查 | 常见原因 |
|---|---|---|
| 输出截断 | finish/stop reason、token 使用 | 输出上限、上下文占满、停止串 |
| JSON 偶发无效 | Schema 模式、模型版本、原始错误 | 自由文本模式、复杂 Schema、截断 |
| TTFT 高 | 排队、输入 token、供应商 | 长 prompt、冷启动、限流、拥塞 |
| 输出慢 | TPOT、输出长度、并发 | decode、服务批处理、网络流 |
| 成本突增 | token、重试、Agent 步数 | 历史膨胀、循环、fallback、重复检索 |
| 同题结果变化 | model/prompt/data 版本、采样 | 概率生成、服务升级、上下文差异 |

## 常见误区

1. 写好 system prompt 就能保证权限：错误，权限必须在应用/工具层。
2. JSON 可解析就能执行：错误，还要业务和授权校验。
3. temperature=0 就无需回归测试：错误，模型与服务仍会变化。
4. 上下文越长答案越好：错误，噪声、成本和 lost-in-the-middle 会增加。
5. 流式输出更省 token：错误，它主要改善感知延迟。
6. 429 立即重试越快恢复：错误，会放大拥塞。
7. fallback 模型可无测试替代：错误，能力和格式不同。
8. 抽象一个统一 SDK 就能屏蔽所有供应商差异：错误，能力语义无法完全抹平。
9. 记录全部 prompt 最方便排障：错误，可能泄露隐私与密钥。
10. 模型调用失败只分成功/失败：错误，需要区分限流、超时、拒绝、截断、Schema 与业务错误。

## 自测题与答案

1. **模型输出为何是不可信输入？** 它受概率、提示、数据和版本影响，可能语法正确但事实/权限错误。
2. **structured output 解决什么？** 提高结构语法可靠性，不解决业务真实性和授权。
3. **工具结果为何不能当高优先级指令？** 外部内容可能被攻击者注入，工具只返回数据。
4. **SSE 断开意味着什么？** 只证明客户端连接断开，需显式传播取消并确认上游状态。
5. **何时不重试？** 永久参数/权限/内容错误、预算耗尽或副作用状态未知且无幂等保护时。
6. **为什么预留输出 token？** 总上下文通常包含输入与生成，输入占满会截断/拒绝输出。
7. **fallback 为什么需回归集？** 模型对 Schema、工具、语言和安全的表现不同。
8. **成本为何不只算模型？** 还有检索、rerank、工具、重试、日志、人工和基础设施。

版本边界：消息角色、Schema、缓存计价和错误码随 API 变化；以目标供应商当前文档为准，通用原则是验证、预算、可观测和不把模型当安全边界。
