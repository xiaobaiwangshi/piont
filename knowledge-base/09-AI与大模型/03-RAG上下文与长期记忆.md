# RAG、上下文与长期记忆

## 学习目标

完成本章后，应能设计一条从文档进入知识库到带引用回答的完整链路，区分检索、生成和记忆，并能解释权限、更新、召回、幻觉和评测失败。

RAG 不是“接一个向量数据库”。它是数据工程、搜索、上下文工程和生成评测的组合。

## 为什么需要 RAG

RAG 主要解决：

- 模型参数中没有企业私有或最新事实。
- 回答需要引用、追溯和权限过滤。
- 事实更新频繁，不适合反复微调权重。
- 需要让错误可定位到解析、索引、检索或生成环节。

RAG 不自动保证正确。若源文档错误、权限缺失、检索漏召回或模型忽略证据，回答仍会失败。

## 完整数据链

```text
数据源
→ 解析/OCR/版面恢复
→ 清洗、去重、标题/表格/列表结构
→ chunk + metadata + ACL + version
→ embedding/稀疏索引
→ query 理解/重写
→ 权限过滤 + 召回
→ rerank/去重/多样性
→ context packing + 引用
→ 生成
→ 检索/回答/引用评测
→ 更新、删除和重建
```

任何一步都应保留 document ID、版本、页码/段落、权限与处理流水线版本，便于重建和追踪。

## 文档解析

PDF 可能包含可复制文本、扫描图、双栏、页眉页脚、脚注、跨页表格和公式。`pdftotext` 只能提取文本层，OCR 只能识别像素，二者都不自动恢复阅读顺序和语义结构。

处理顺序：

1. 检测文本层、页数、语言、加密和版式。
2. 文本 PDF 优先提取；扫描页定向 OCR，不无条件整库 OCR。
3. 去页眉页脚、水印和重复页码，但保留页码映射。
4. 恢复标题层级、段落、列表、表格与图片说明。
5. 用源文件 hash + parser/OCR 版本生成可重放产物。

表格转纯文本可能丢列关系；关键表格可保存结构化 HTML/Markdown 与页面截图引用。解析正确性应通过抽样页面对照，不只看“有文字”。

## Chunk 策略

chunk 过小会丢上下文，过大会降低定位精度并浪费 prompt。常见策略：

- 固定 token + overlap：简单，可能切断结构。
- 按标题/段落：保留语义层级，需可靠解析。
- 递归分隔：依次按章节、段落、句子切分。
- 父子 chunk：小块检索，返回较大父块给模型。
- 语义切分：按话题变化，成本和稳定性更复杂。

每块应带标题路径、文档/版本、页码、时间、语言、ACL、实体和业务类型等 metadata。overlap 不是越大越好，会增加重复召回和索引成本。

## 稀疏与向量检索

### BM25/关键词

擅长精确术语、编号、姓名、错误码和罕见词；可解释且易过滤，但对同义表达较弱。

### Dense Embedding

把 query 和文档映射到向量空间，适合语义相似。相似度可用 cosine、dot product 或距离；模型是否归一化、索引度量是否匹配必须核对。

### ANN

近似最近邻用少量召回损失换延迟和内存。HNSW、IVF 等参数影响 build 时间、索引大小、查询延迟和 Recall，不存在脱离数据集的“最佳参数”。

### Hybrid

并行召回 BM25 与向量结果，再用加权、归一化或 RRF 融合，能兼顾精确词与语义。不同检索分数通常不可直接相加，必须做可解释的融合和评测。

## Query 理解与 Rerank

- query rewrite：补全省略、规范术语，但可能改错意图。
- multi-query：生成多个表达增加召回，同时提高成本与噪声。
- HyDE：生成假想文档再做向量检索，适用于某些语义空间，假想内容不是事实。
- RAG-Fusion：多查询召回后融合排名。
- metadata filter：租户、时间、产品、权限等应尽量在检索侧强制过滤。
- reranker：对候选做更精细的 query-document 相关性打分，成本通常高于初始召回。

先扩大召回再 rerank 是常见模式，但候选过多会增加延迟，候选过少会让 reranker 无法找回漏掉的正确文档。

## Context Packing

最终上下文不是简单拼接 top-k：

1. 严格 ACL 过滤。
2. 去除近重复和冲突版本。
3. 优先高相关且覆盖不同子问题的块。
4. 带标题、来源和引用 ID。
5. 在 token 预算内保留问题、固定指令和输出空间。
6. 明确要求证据不足时回答“不知道”或请求信息。

可用 parent expansion、摘要或压缩降低 token，但压缩会丢细节，摘要也可能幻觉。高风险场景应让答案引用原文块而非只引用摘要。

## 四种状态/记忆

| 类型 | 例子 | 生命周期 | 真相与风险 |
|---|---|---|---|
| 当前消息 | 本轮问题 | 单次请求 | 用户输入不可信 |
| 工作记忆 | 最近步骤、会话摘要 | 任务/会话 | 摘要可能丢失或写错 |
| 长期记忆 | 用户偏好、历史决策 | 跨会话 | 需同意、来源、过期、删除 |
| 权威知识 | 制度、产品、订单 | 业务系统/知识库 | 必须按权限实时读取 |

长期记忆写入要有明确策略：哪些事实可记、由谁确认、来源是什么、何时过期、冲突如何处理、用户如何查看/删除。不要把模型推断当成用户事实永久保存。

摘要应保存关键实体、已确认事实、未完成动作和决策，而非“压缩全部聊天”。重要业务状态应结构化持久化，不依赖自然语言摘要恢复。

## 评测

### 检索指标

- Recall@K：相关文档中有多少出现在前 K；若每题只有一个标准证据，也常看是否命中。
- Precision@K：前 K 中相关文档比例。
- MRR：第一个相关结果排名倒数的平均值。
- nDCG：考虑分级相关性和位置折损。

示例：5 个问题中，正确证据进入 top-5 的有 4 个，则 hit-style Recall@5 为 80%。这不代表答案正确。

### 生成指标

- context relevance：提供的上下文是否相关。
- faithfulness/groundedness：回答声明能否由上下文支持。
- answer correctness/relevance：是否正确回答用户问题。
- citation correctness/completeness：引用是否真的支持声明、重要声明是否都有来源。

评测集应包含：可回答、不可回答、多个版本冲突、权限不足、表格问题、跨块问题、精确编号和模糊表达。

## GraphRAG 与多模态边界

GraphRAG 适合多跳实体关系、全局主题和需要显式关系的问题；建设实体/关系抽取、消歧、更新和图查询的成本很高。若普通 hybrid + rerank 已满足，不必为了名称引入图。

多模态 RAG 需处理图片/图表/页面坐标与文本对齐。仅用 OCR 文本会丢视觉关系；仅用图片 embedding 又难做精确引用。按任务决定是否保存区域级证据。

## 典型失败证据链

| 现象 | 检查顺序 |
|---|---|
| 正确文档完全找不到 | 是否入库 → parser/chunk → ACL/filter → query → sparse/dense Recall@K |
| 找到但排名低 | 候选分数 → hybrid 融合 → rerank 数据/模型 → 重复块 |
| 上下文正确但答案错 | context packing → 指令 → 模型 → 冲突证据 → faithfulness |
| 引用页码不对 | 页码映射 → chunk provenance → 版本 → 生成引用 ID |
| 更新后仍答旧内容 | 增量事件 → 删除旧 chunk → 索引一致性 → cache → 版本过滤 |
| 用户看到越权资料 | ACL 入库/查询过滤 → cache key → tenant → 日志；这是安全事故 |

## 常见误区

1. RAG 等于向量数据库：错误，它是完整数据与评测链。
2. chunk 越小召回越准：错误，可能丢语义和跨句关系。
3. overlap 越大越安全：错误，会重复、增成本和挤上下文。
4. 向量检索一定优于 BM25：错误，编号/专名常由稀疏检索更好。
5. top-k 越大答案越好：错误，噪声和 token 成本增加。
6. reranker 能补回没召回的文档：错误，它只能重排候选。
7. 检索命中就说明答案正确：错误，模型可能不用或误用证据。
8. 聊天记录就是记忆：错误，缺少生命周期、事实和权限语义。
9. GraphRAG 是普通 RAG 的必然升级：错误，取决于多跳关系需求。
10. 权限可写进 prompt：错误，必须在数据/检索层强制执行。

## 自测答案

1. **为何保留 provenance？** 用于引用、版本、删除、权限、重建和故障定位。
2. **父子 chunk 解决什么？** 小块精确检索、大块提供完整上下文。
3. **hybrid 为什么需融合？** 稀疏与向量分数口径不同，需统一排名而非直接相加。
4. **Recall@K 高但答案差查哪里？** rerank/context packing、冲突、提示、模型使用证据和答案评测。
5. **长期记忆为何不能自动全写？** 推断可能错误，还涉及隐私、冲突、过期和删除。
6. **什么情况考虑 GraphRAG？** 问题真正依赖实体多跳/全局结构，且普通检索不足时。
