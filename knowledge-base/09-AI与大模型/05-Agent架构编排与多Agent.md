# Agent 架构、编排与多 Agent

## 学习目标

Agent 不是“循环调用大模型”的同义词，而是一个在约束内观察状态、选择动作、执行工具、处理结果并终止的系统。本章从十年全栈开发者熟悉的状态机、工作流和分布式任务出发，说明何时需要自主决策，何时普通代码更可靠。

## 最小 Agent 模型

```text
输入目标 + 身份/权限 + 初始状态
→ 观察当前状态
→ 选择下一动作（代码规则或模型）
→ 校验动作和预算
→ 执行工具
→ 记录结果并更新状态
→ 达成目标 / 请求人工 / 失败 / 超预算时终止
```

系统至少显式保存：目标、当前步骤、已知事实、工具结果、错误、剩余步数、时间/费用预算和终止原因。模型负责不确定语义决策；权限、金额、状态转换和终止规则由确定性代码负责。

## Workflow 与自主 Agent

| 形态 | 决策方式 | 适合问题 | 主要风险 |
|---|---|---|---|
| 普通函数/规则 | 代码固定 | 输入输出明确、流程稳定 | 规则膨胀 |
| Workflow | 路径基本预定义，局部用模型 | 审批、工单、内容流水线 | 分支和补偿遗漏 |
| Router | 模型/分类器选择既有路径 | 多意图客服、专家分流 | 误路由 |
| Agent | 模型动态选择动作和顺序 | 开放目标、信息不完整 | 不终止、越权、成本不可控 |

选择顺序应是普通代码 → workflow → 局部 Agent。能用 SQL、规则或有限状态机稳定完成的环节，不因“智能化”改成自由循环。

## 常见编排模式

### ReAct

模型根据观察选择动作，再把工具结果作为新观察继续。它适合步骤数未知、需要边查边判断的问题。生产实现不必暴露内部思维过程，应记录可审计的动作理由摘要、工具输入输出和状态变化。

风险是重复搜索、过早结论和无限循环。需要 `max_steps`、重复动作检测、工具/时间/费用预算和明确终止条件。

### Plan-and-Execute

先生成可修订计划，再逐步执行。适合目标可分解、步骤较长的任务。计划只是候选，不是事实；每一步仍需校验前置条件，外部状态改变后应重规划而非机械执行旧计划。

### Router

先按意图、风险、租户或能力分流到固定链路。低风险、高置信度可自动执行；低置信度转人工或保守路径。路由结果应可解释、可回放，并对“不属于任何类”保留兜底。

### Reflection/Critic

生成后再检查约束、证据或格式，可提升部分任务质量，但不能把同一模型的自评当独立事实。安全、金额和权限仍由规则、工具查询或人工确认；反思轮数有固定上限。

### Supervisor/Worker

Supervisor 拆分任务、分派 worker、合并结果。适合角色确实具有不同权限、上下文、工具或可并行子任务的场景。Supervisor 不是无限上级：它也必须受预算、终止、证据和授权约束。

## 图、状态与 Checkpoint

用图表示节点和允许的边，用持久化状态承载节点输入输出：

```text
receive → classify → retrieve → draft → validate
                              ↘ approve → execute → verify
                              ↘ reject / manual / failed
```

- 节点应尽量幂等，输入输出结构化。
- 边条件由可测试的状态决定，不只依赖自然语言。
- checkpoint 保存可恢复状态；进程重启后从最后一个已确认边界继续。
- 外部副作用与 checkpoint 不是天然原子事务，要用幂等键、outbox/inbox、查询确认或补偿处理间隙失败。

框架中的 graph、node、edge、state、interrupt、checkpoint API 会变化；这些概念比具体调用方式稳定。

## 终止与预算

每次运行至少设置：

- 最大步骤、最大模型调用和最大工具调用。
- 总超时、单步超时、最大输入/输出 token 和费用上限。
- 连续重复动作、连续无新信息和同类错误阈值。
- `completed`、`failed`、`cancelled`、`waiting_human`、`budget_exceeded` 等终态。

“模型说完成”只是一个信号。最终完成条件应检查产物、业务状态、引用证据或验证工具结果。

## Human-in-the-Loop

人工介入适合三类点：信息不足、风险过高、系统置信度不足。中断时持久化完整 checkpoint，并向审批者展示动作、对象、关键参数、证据、影响范围和费用。

审批必须绑定 task、step、参数摘要、数据/工具版本和有效期；参数变化后原批准失效。人工拒绝也是明确事件，不能让 Agent 换工具绕过。

## 多 Agent 何时值得

只有出现以下至少一项真实差异时才优先考虑多 Agent：

- 子任务可以独立并行，且合并成本低。
- 角色需要不同权限、工具或数据隔离。
- 需要不同模型能力或上下文窗口。
- 单一上下文过大，需要明确分区并由结构化产物交接。

如果只是给同一个模型起“产品经理、工程师、评审员”三个名字，通常增加 token、延迟和故障面，却没有真正隔离。先用单 Agent + 多阶段 workflow 验证价值。

## 多 Agent 协作协议

每个任务交接至少包含：目标、输入、允许动作、禁止动作、输出 Schema、截止时间、预算、完成定义和来源。共享黑板/消息队列中的事实要有作者、时间、版本和可信等级。

常见故障：循环委派、双方等待、重复执行、结论冲突、旧状态覆盖和上下文污染。控制方式包括有向任务图、唯一 owner、租约、最大委派深度、冲突仲裁规则和全局预算。

## 架构选择案例

### 企业知识助手

使用 Router + RAG + 引用校验即可；没有写操作时通常不需要自由 Agent。低召回或无权限文档不能靠模型“补全”。

### 工单处理

固定状态机负责分类、补信息、审批、执行、验证和关闭；模型只做分类、摘要和候选方案。写入工单、通知和退款必须幂等。

### 代码/运维助手

读取、分析、修改、验证是图节点；shell、部署和删除分别使用沙箱、allowlist 与人工批准。验证失败回到修订节点，达到步数上限则保留产物并转人工。

## 常见误区

1. Agent 越自主越先进：错误，可控地完成目标才是价值。
2. Prompt 能替代状态机：错误，Prompt 不能提供持久化和原子状态转换。
3. 模型说“完成”即可结束：错误，要验证真实产物或业务状态。
4. Reflection 能保证正确：错误，它仍可能重复同一偏差。
5. Checkpoint 等于副作用恰好一次：错误，数据库与外部系统之间仍有失败窗口。
6. 多 Agent 天然优于单 Agent：错误，通信和协调成本可能更高。
7. 给角色不同名字就是隔离：错误，权限、工具和上下文必须真实隔离。
8. 失败后从头重跑最简单：错误，可能重复费用和副作用。

## 自测题与答案

1. **什么时候普通 workflow 优于 Agent？** 路径、规则和完成条件稳定，动态决策价值小的时候。
2. **最重要的终止控制有哪些？** 完成条件、步数、超时、费用、重复动作和人工/失败终态。
3. **为何 checkpoint 后仍需幂等？** 外部副作用成功与 checkpoint 落盘之间可能崩溃。
4. **多 Agent 的合理依据是什么？** 可并行性或真实的权限、工具、模型、上下文隔离。
5. **人工批准应绑定什么？** 具体任务、步骤、动作参数、版本和有效期。
6. **如何判断 Agent 真完成？** 用业务查询、产物校验、测试或引用证据验证，而非只信自然语言。

版本边界：ReAct、路由、图和 checkpoint 是稳定模式；LangGraph、AutoGen、CrewAI 等框架 API 快速变化，选型时按目标版本验证持久化、并发、审批和恢复语义。
