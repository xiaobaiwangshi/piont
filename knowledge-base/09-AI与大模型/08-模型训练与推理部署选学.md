# 模型训练与推理部署选学

## 定位

本章帮助 AI Agent 工程师判断何时需要改模型或自托管，并理解服务容量边界。训练框架、CUDA kernel 和大规模集群实践属于选学；默认先使用模型 API、Prompt、RAG、工具和评测解决应用问题。

## 从最小手段开始

| 问题 | 优先手段 | 何时考虑下一层 |
|---|---|---|
| 输出格式/规则不稳 | Schema、校验、few-shot、workflow | 大量稳定模式仍失败 |
| 缺少私有/新知识 | RAG、权威工具 | 检索后仍不能形成所需行为 |
| 固定任务风格/行为 | SFT/LoRA | 有高质量示例和稳定评测收益 |
| 领域语言/知识分布差异大 | continued pretraining | 数据量、算力和风险可承担 |
| 偏好/安全行为 | DPO/RLHF 等 alignment | 有成对偏好/奖励信号与专业团队 |
| 隐私、成本、延迟、离线 | 自托管/小模型 | API 无法满足明确约束 |

微调不能可靠注入频繁变化的事实，也不替代实时权限和数据库查询。先建立基线和评测集，否则无法判断训练是否真的改善。

## 数据工程

训练数据比框架参数更重要：来源和许可、个人/敏感数据、去重、质量、长度、语言/领域分布、冲突、污染、训练/评测泄漏都需记录。

SFT 示例通常包含输入、期望输出及必要上下文；工具/Agent 数据还要表达工具 Schema、合法动作、错误恢复和终止。错误轨迹不能不加区分地当正例。

数据版本应有不可变 manifest、内容哈希、清洗规则和删除/追踪能力。模型输出合成数据需要抽样人工验证，避免把模型偏差递归放大。

## SFT、PEFT 与 LoRA

SFT 用监督样本优化下一个 token 目标，使模型学习目标任务和响应分布。全量微调更新全部参数，资源和灾难性遗忘风险更高。

PEFT 只训练少量新增/选定参数。LoRA 对目标权重加入低秩增量，参数量公式见[大模型核心机制](../07-核心机制深入/10-大模型核心机制.md)。需要选择 target modules、rank、学习率、数据混合和 checkpoint；“可训练参数少”不代表不需可靠数据与评测。

合并 LoRA 便于单适配器部署；运行时挂载便于多租户/任务切换，但增加显存、路由、并发和版本治理复杂度。

## Continued Pretraining 与 Alignment

持续预训练用领域无标注文本继续语言模型目标，适合领域表达/分布差异显著的场景；成本高，可能改变通用能力，之后通常仍需指令微调。

RLHF/PPO、DPO 等用于偏好/对齐。DPO 使用偏好对简化部分训练流程；PPO/RLHF 涉及奖励模型、策略和参考模型等。算法名称不保证事实正确或安全，reward hacking、偏好偏差和能力回退仍需评测。

对 Agent 转型，先理解目的、数据和风险；只有岗位/项目明确需要训练平台时再进入公式、代码和集群实操。

## 分布式训练概念

- Data Parallel：各设备持模型副本，切分 batch 并同步梯度。
- Tensor Parallel：把单层张量/计算切到多设备，通信频繁。
- Pipeline Parallel：按层切阶段，以 micro-batch 填充流水线，有 bubble。
- Sequence/Context Parallel：沿序列维拆分部分计算/状态。
- Expert Parallel：MoE 专家分布到不同设备，依赖 all-to-all。
- ZeRO/FSDP：分片优化器状态、梯度和权重，降低单卡静态显存。

真实集群还受网络拓扑、collective、负载不均、checkpoint、故障恢复和数据吞吐影响。DeepSpeed、FSDP、Megatron 等 API/能力随版本变化，资料中的命令不能直接当当前生产配置。

## 推理服务路径

```text
请求入队 → tokenize → scheduler/batching → prefill
→ KV Cache 分配 → iterative decode → detokenize/stream
→ 结束/释放缓存
```

- TTFT：首 token 时间，受排队、tokenize 和 prefill 影响。
- TPOT/ITL：后续 token 间隔，受 decode 调度和带宽影响。
- 端到端延迟：排队 + TTFT + 输出 token 的逐步生成。
- 吞吐：requests/s 或 tokens/s，必须注明输入/输出分布和并发。

只报 tokens/s 没有硬件、模型、量化、batch、上下文和 SLO，几乎不可比较。

## Batching 与调度

静态 batching 等待凑批，简单但易被不同长度拖累。Continuous batching 在请求生成过程中动态加入/移出序列，提高利用率；高吞吐可能增加排队和单请求长尾。

调度器要平衡 prefill 与 decode、短请求与长请求、租户公平和优先级。长 Prompt 会占用计算与 KV；需限制输入/输出、并发和每租户 token 预算。

## PagedAttention 与 KV Cache

KV Cache 随层数、token、KV heads、head dim、精度和并发增长，数量级公式见深入章。PagedAttention 类实现把 KV 分块映射，降低连续内存预留和碎片，支持更灵活共享/调度；不消除 KV 本身，也不保证所有负载加速。

Prefix caching 可复用相同前缀计算/KV，但命中取决于 token 完全一致、模型/适配器/参数兼容，并需要租户隔离和淘汰策略。

## 量化与 Speculative Decoding

权重/激活/KV 量化用更低位宽换显存和带宽，质量取决于模型、校准、量化粒度、kernel 和硬件。必须在目标任务、长上下文和工具调用结构化输出上回归。

Speculative decoding 用较小 draft model 提议多个 token，再由 target model 验证；保持目标分布的算法可降低串行 decode 次数，但收益取决于接受率、draft 成本、batch 和实现，不能只看理想倍数。

## 自托管决策

评估：模型质量、许可证/商用条款、数据驻留、峰值与平均负载、GPU 利用率、延迟 SLO、运维团队、升级/安全补丁和容灾。低利用率时 API 往往更省；稳定高负载或严格数据/离线要求可能支持自托管。

混合方案可把普通请求路由到小模型，复杂/高风险请求到强模型，但路由错误和双套评测/运维也有成本。先通过 trace 得到真实 token、延迟和质量分布再决策。

## 常见误区

1. 知识不足就微调：错误，动态事实通常先用 RAG/工具。
2. LoRA 很小所以训练很简单：错误，数据、评测和版本仍复杂。
3. Continued pretraining 等于指令微调：错误，目标和数据不同。
4. Alignment 能保证事实正确：错误，它主要优化偏好/行为目标。
5. 模型能放入显存就能高并发：错误，KV、workspace 和调度还占资源。
6. 量化只降显存不降质量：错误，需按任务和实现评测。
7. PagedAttention 消除 KV：错误，它优化分配和碎片。
8. 自托管一定比 API 便宜：错误，需计入利用率、人员、容灾和升级。

## 自测题与答案

1. **新政策知识优先怎么做？** 权威数据源 + RAG/工具，不把易变事实烤进权重。
2. **何时考虑 SFT/LoRA？** 任务稳定、有高质量示例、基线明确且回归集证明收益时。
3. **Data Parallel 与 Tensor Parallel 差别？** 前者切 batch/同步梯度，后者切单层张量与计算。
4. **TTFT 与 TPOT 分别代表什么？** 首 token 延迟和后续 token 间隔。
5. **为什么吞吐数字要附负载？** 输入输出长度、batch、并发、硬件和 SLO 会显著改变结果。
6. **自托管前最需要什么数据？** 实际请求量、token/长度分布、质量目标、延迟和合规约束。

版本边界：推理框架、量化 kernel、GPU 和分布式训练栈变化很快；本章保留稳定机制，具体 vLLM/TGI/TensorRT-LLM/DeepSpeed 配置应以目标版本官方文档和实测为准。
