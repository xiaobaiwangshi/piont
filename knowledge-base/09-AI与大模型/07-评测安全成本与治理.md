# 评测、安全、成本与治理

## 学习目标

Agent 的质量不是“回答看起来不错”，而是能否在权限、成本和时间约束内可靠完成目标。本章建立从节点到业务结果的评测体系，并把 prompt injection、越权、数据泄漏和危险工具纳入发布门禁。

## 四层评测对象

| 层级 | 评测对象 | 典型指标/断言 |
|---|---|---|
| 节点 | 分类、抽取、结构化输出、工具参数 | accuracy/F1、Schema 通过率、字段规则 |
| 检索 | query、候选、rerank、引用 | Recall@K、MRR/nDCG、ACL 命中、引用覆盖 |
| 轨迹 | 动作顺序、工具、重试、终止 | 成功步骤、非法动作、重复调用、步数/成本 |
| 端到端 | 用户目标和业务状态 | task success、正确办理、人工接管、SLO、投诉 |

端到端指标最重要，但只看最终结果难以定位；四层必须用同一 case/task/trace ID 串联。

## 评测集

Golden set 应来自真实任务分布，覆盖正常、边界、对抗、权限、依赖失败和历史事故。每个 case 包含：输入、身份/租户、冻结数据、允许/禁止动作、期望业务结果、可接受轨迹、成本/延迟上限和评分版本。

拆分：

- 开发集用于调试 Prompt 和 workflow。
- 回归集用于每次发布，避免为单个 case 反复调参造成泄漏。
- 保留集周期性评估泛化，不参与日常修改。
- 线上样本经脱敏、授权和人工确认后回流。

数据随业务变化会过期；需要 owner、来源、版本、更新时间和适用范围。

## 确定性断言优先

能用代码判断的不要先交给 LLM judge：JSON Schema、ID/金额、引用是否存在、租户是否匹配、禁止工具是否被调用、是否产生重复副作用、最终数据库状态和步数/费用上限。

工具在离线评测中用冻结响应或 mock：既能复现，又不会真实发消息、退款或部署。对重试、超时、状态未知和审批拒绝主动注入故障。

## 语义评分与人工复核

开放回答可评估正确性、相关性、完整性、groundedness、引用一致性和表达质量。使用 LLM judge 时：

- 明确 rubric 和分值锚点，尽量要求基于给定证据。
- 固定 judge model、prompt、参数和版本。
- 用交换答案顺序、隐藏来源等方式检查位置/风格偏差。
- 与人工标注计算一致性，并抽查分歧、临界和高风险样本。
- judge 不能判定真实权限和业务状态，仍查询权威系统。

人工评审适合高风险、主观质量、新分布和裁决样本；记录理由而非只给分。

## 线上反馈

观察用户修正、重新提问、撤销、人工转接、工具失败、投诉和业务回滚。点赞/点踩是弱信号，受表达风格和用户预期影响，不能直接等于事实正确。

新版本用 shadow/canary/分流逐步发布，按租户和用例比较成功率、风险、成本与长尾延迟。出现安全或业务回归时能按 prompt/model/tool/workflow 版本回滚。

## 威胁模型

### Prompt Injection

- 直接注入：用户要求忽略系统规则、泄露秘密或执行越权动作。
- 间接注入：网页、PDF、邮件、RAG 文档或工具结果包含恶意指令。

内容分类器和提示语只是信号。根本控制是指令/数据隔离、最小权限、工具策略校验、秘密最小暴露和高风险审批。

### 权限提升与 confused deputy

攻击者让拥有更高权限的 Agent 代为访问或写入。租户/user/scope 从认证上下文注入；每次检索和工具调用服务端重新授权，不能继承模型声称的身份。

### 数据泄漏与跨租户记忆

风险来自上下文、日志、trace、缓存、embedding/索引、长期记忆、错误消息和模型 provider。所有数据面按租户/用户 ACL 隔离；敏感字段最小化、加密、脱敏并设保留/删除策略。缓存 key 必须包含权限边界。

### 危险工具与供应链

shell、浏览器、文件、数据库写、消息和部署工具可造成真实损害。MCP server、插件、模型、依赖、Prompt/模板和外部数据源都是供应链；固定来源/版本，审查权限，隔离执行，保留撤销机制。

## 分层控制

```text
身份与租户
→ 输入/来源标签
→ 模型可见信息最小化
→ 工具 allowlist + Schema
→ 服务端业务/授权校验
→ 沙箱、网络和资源限制
→ 高风险人工审批
→ 输出验证/脱敏
→ 审计、告警和事件响应
```

任何单层都可能失败。尤其不能把“模型拒绝”当作数据库、支付或部署权限控制。

## 发布门禁

每个候选版本同时比较：

- 质量：端到端成功率、检索/引用、关键场景回归。
- 安全：越权成功数必须为零，高风险动作无批准执行必须为零。
- 可靠性：恢复、幂等、取消、依赖故障和长尾 SLO。
- 成本：每成功任务成本、token、工具和人工时间。

设置硬门禁与非劣化阈值。平均质量提升不能抵消权限绕过；成本下降也不能以隐藏失败或减少必要证据实现。

## 版本和可复现性

评测报告至少记录代码/graph、Prompt、模型、工具 Schema/实现、检索索引/语料、评测集、judge、采样参数和运行时间。云模型可能不能完全复现，因此保存响应元数据和统计置信区间，不宣称一次运行的微小差异必然有效。

对于通过率 `p̂=x/n`，样本越少不确定性越大。比较版本要同时看 case 差异和置信范围，不能用 10 个样本从 8/10 到 9/10 就断言稳定提升。

## 事件响应

发现越权、泄漏或错误副作用时：暂停相关工具/版本 → 保存 trace 和审计证据 → 撤销 token/权限 → 确认影响租户和数据 → 补偿/通知 → 修复控制层 → 将事故转为回归/对抗 case。

不要把完整敏感 Prompt 到处复制做排障；使用受控引用、脱敏样本和最小访问权限。

## 常见误区

1. Demo 成功等于可上线：错误，未覆盖分布、故障和攻击。
2. 最终答案正确就够：错误，轨迹可能越权或产生错误副作用。
3. LLM judge 是客观真值：错误，会受模型、Prompt、顺序和风格影响。
4. 点赞率就是正确率：错误，它只是有偏弱信号。
5. Prompt 写“不得泄密”即可：错误，权限和数据最小化必须在系统层。
6. RAG 文档是可信指令：错误，外部内容可能被污染或注入。
7. 多租户共用缓存没问题：错误，key/索引/记忆必须绑定权限范围。
8. 平均成本下降就更好：错误，需按成功任务和长尾/风险归因。

## 自测题与答案

1. **为何同时评测节点、轨迹和端到端？** 分别定位局部错误、过程风险和真实业务结果。
2. **什么优先用确定性断言？** Schema、金额、ID、权限、工具调用、业务状态和预算等可计算事实。
3. **间接注入来自哪里？** 网页、文档、邮件、RAG 和工具结果等不可信数据。
4. **LLM judge 需要怎样校准？** 固定版本/rubric，与人工一致性比较并抽查分歧。
5. **安全门禁为何不能用平均质量抵消？** 一次越权或泄漏可能造成不可接受的真实损害。
6. **线上事故怎样转化为资产？** 保存受控证据，修复控制层，并加入回归和对抗评测集。

版本边界：模型评测库、Agent tracing 和 guardrail 产品快速演进；稳定核心是分层对象、确定性断言、威胁模型、版本记录和业务结果门禁。
