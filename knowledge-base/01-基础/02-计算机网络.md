# 计算机网络

## 学习目标与阅读方式

读完本章应能从应用数据出发，解释它如何经过 DNS、链路、路由、TCP/QUIC、TLS 和 HTTP 到达远端服务；能够计算 CIDR、窗口吞吐与带宽时延积；能够从连接状态、抓包字段、代理日志和超时位置建立故障证据链。

先修知识：二进制与字节、进程/文件描述符、延迟/吞吐/带宽。Linux 协议栈、队列、网卡和内核实现细节放在[协议栈与网络性能](../07-核心机制深入/02-协议栈与网络性能.md)，本章只在需要理解协议时引用。

文中的命令用于说明应观察什么，不要求在本阶段搭建或运行实验环境。

## 基础知识

### 分层模型

OSI 七层便于学习；实际工程更常用 TCP/IP 分层：

| 层 | 关注内容 | 常见协议/对象 |
|---|---|---|
| 应用层 | 应用语义 | HTTP、DNS、SSH、SMTP |
| 传输层 | 端到端传输 | TCP、UDP、QUIC |
| 网络层 | 跨网络寻址与路由 | IP、ICMP |
| 链路层 | 同一链路传输 | Ethernet、ARP、Wi-Fi |
| 物理层 | 比特与信号 | 网线、光纤、无线电 |

分层是逻辑抽象，不代表所有协议都能严格塞入单一层。例如 ARP 位于链路层和网络层边界，TLS 通常位于应用与传输之间。

#### 封装与解封装

发送时，上层数据逐层增加控制信息：

```text
应用消息
→ TCP segment / UDP datagram
→ IP packet
→ Ethernet frame
→ 比特/信号
```

接收端按相反方向校验和拆解。每一层只理解自己的首部和语义；代理、NAT、隧道等中间设备可能在途中终止、修改或再次封装部分层。

### 链路层：Ethernet、ARP/NDP 与 VLAN

- Ethernet frame 在一个二层广播域内按 MAC 地址交付。
- 交换机学习“源 MAC → 端口”，再根据目的 MAC 转发；未知单播和广播可能被泛洪。
- IPv4 使用 ARP 把同链路 IPv4 地址解析为 MAC；IPv6 使用 Neighbor Discovery，并由 ICMPv6 承载相关消息。
- VLAN 用 802.1Q 标签把同一物理交换网络划成多个逻辑广播域；跨 VLAN 通信需要三层路由。

MAC 地址只在当前链路有意义。访问远端 IP 时，主机通常解析的是默认网关 MAC，而不是远端服务器 MAC。

#### MTU 与 MSS

MTU 是链路可承载的网络层报文上限。以常见 Ethernet MTU 1500 为例，在没有 TCP 选项时：

```text
IPv4 TCP MSS ≈ 1500 - 20(IP) - 20(TCP) = 1460 bytes
IPv6 TCP MSS ≈ 1500 - 40(IPv6) - 20(TCP) = 1440 bytes
```

隧道、TCP 选项和路径中的更小 MTU 会降低有效 MSS。具体值应由握手选项和 Path MTU Discovery 决定，不能永久背成 1460。

### IP、子网与路由

- IP 地址标识网络接口。
- 子网掩码/CIDR 区分网络前缀与主机部分。
- 主机先判断目标是否同网段；同网段直接解析链路地址，不同网段交给默认网关。
- 路由器根据路由表选择下一跳，遵循最长前缀匹配。

传统 A/B/C 类地址只适合历史学习，现代网络使用 CIDR。

#### CIDR 计算

IPv4 `/n` 前缀共有 `2^(32-n)` 个地址。传统普通子网通常扣除网络地址和广播地址，但 `/31` 点到点链路和 `/32` 主机路由有专门语义，不能机械减 2。

例：`192.0.2.64/26` 的块大小为 `2^(32-26)=64`，地址范围是 `.64` 到 `.127`，传统可用主机通常是 `.65` 到 `.126`。

IPv6 地址为 128 位，通常按前缀分配；没有 IPv4 式广播，使用 multicast 与 Neighbor Discovery。IPv6 不是“地址更长的 IPv4”，首部、分片和邻居发现行为都有差异。

#### ICMP、NAT 与端口

- ICMP 报告差错并支持诊断，例如 unreachable、time exceeded、Packet Too Big；完全阻断会破坏路径发现和排障。
- NAT/PAT 常把私网 `source_ip:source_port` 映射为公网端点，并用 conntrack 保存状态。
- TCP/UDP 端口标识主机上的通信端点。客户端临时端口、NAT 映射、TIME_WAIT 和连接跟踪表都可能成为连接容量上限。

路由决定下一跳，NAT 改写地址/端口，两者不是同一件事。路由表有多条匹配项时选择最长前缀，再由度量值和策略决定具体路径。

### TCP

TCP 提供面向连接、可靠、有序的字节流：

1. 三次握手协商初始序列号并确认双方收发能力。
2. 序列号、ACK、校验和、重传保证可靠性。
3. 接收窗口负责流量控制；拥塞窗口负责网络拥塞控制。
4. 关闭通常需要双方分别发送 FIN，因此常见四次挥手。

TCP 没有消息边界，应用协议必须用长度、分隔符或固定格式解决粘包/拆包。

#### 三次握手与状态

```text
Client                                Server
SYN, seq=x          ---------------->
                    <----------------  SYN+ACK, seq=y, ack=x+1
ACK, ack=y+1        ---------------->
ESTABLISHED                            ESTABLISHED
```

三次握手同时确认双方收发路径、同步初始序列号，并协商 MSS、窗口扩大、SACK 等选项。服务端收到 SYN 后进入半连接阶段，最终 ACK 到达后才进入已建立连接队列；“两次就够”无法让双方都确认对方已收到自己的初始序列信息。

#### 序列号、确认号与重传

TCP 把数据看成连续字节流。假设发送端从序列号 1000 开始发送 1000 字节，则这段数据覆盖 `[1000, 2000)`；接收端回复 `ACK=2000`，表示 2000 之前的字节都已连续收到，下一字节期望是 2000。

- ACK 默认是累计确认；收到 ACK 2000 代表此前连续数据已确认。
- 中间段丢失时，后续乱序段可能触发重复 ACK。
- SACK 选项可告诉发送端已收到哪些不连续区间，避免重传全部后续数据。
- RTO 超时用于没有足够 ACK 线索时重传；快速重传可在典型的多个重复 ACK 后提前重传。具体阈值与算法由实现决定。

RTO 不能直接等于一次 RTT。实现会根据平滑 RTT 和 RTT 抖动估算超时，并设置上下限；过短会产生伪重传，过长会延迟恢复。累计 ACK 只确认连续前缀，SACK 则补充已收到的离散区间。

#### 滑动窗口：流量控制

接收端在 ACK 中通告接收窗口 `rwnd`，表示当前还能接收多少字节。发送端可连续发送未确认数据，只要在途数据没有超过窗口：

```text
已确认                已发送未确认                 允许发送              暂不可发送
|--------------------|---------------------------|--------------------|------>
                  SND.UNA                     SND.NXT
                  <--------- 发送窗口 ----------------->
```

示例：MSS 为 1460 字节，接收窗口为 5840 字节（4 MSS）。发送端无需每发一段就等待，可连续发 4 段。接收端累计确认前两段后，窗口右移，发送端又能补发两段，这就是“滑动”。

接收端处理不及时会缩小 `rwnd`，甚至通告零窗口。发送端停止正常发送并周期性发送窗口探测，防止窗口更新报文丢失后双方永久等待。高带宽网络会使用 Window Scale 扩展窗口，突破 TCP 首部 16 位窗口字段的原始 65535 字节限制。

流量控制保护接收端，不等同于拥塞控制。发送端真实可用窗口近似为：

```text
send_window = min(rwnd, cwnd)
```

其中 `cwnd` 是拥塞窗口，用于保护网络路径。

更完整的发送约束还要扣除已经在途、尚未确认的数据：

```text
new_data_budget ≈ min(rwnd, cwnd) - flight_size
```

若结果小于等于零，发送端需要等待 ACK、窗口更新或重传计时器。即使窗口仍有空间，应用没有继续写 socket、发送缓冲不足或接收端没有及时读取，也会让链路空闲。

例：`rwnd=256KiB`、`cwnd=128KiB`、在途数据 `flight_size=96KiB`，则新数据预算约为 `128-96=32KiB`。接收端还有空间，但网络拥塞窗口是更小约束。

#### 慢启动与拥塞控制

拥塞控制根据丢包、时延或带宽模型调整 `cwnd`：

1. 慢启动：连接开始或严重拥塞恢复后，`cwnd` 从较小值开始；每收到 ACK 增加窗口，一个 RTT 内大致呈指数增长，直到达到 `ssthresh` 或发现拥塞。初始窗口由标准和系统实现决定，不能永久背成 1 MSS。
2. 拥塞避免：超过阈值后增长变缓，经典算法大致每 RTT 增加约 1 MSS。
3. 快速重传/恢复：收到足够的重复 ACK 后推测某段丢失，不等待 RTO；经典 Reno 会降低窗口后继续传输。
4. 超时：通常被视为更严重的拥塞信号，窗口下降更多。

现代 Linux 常使用 CUBIC，而不是纯教材 Reno；也可以使用 BBR 等基于带宽和 RTT 模型的算法。因此“慢启动 → 线性增长 → 窗口减半”是理解框架，不是所有系统每一步的精确实现。

慢启动的“指数增长”来自一个 RTT 内多次 ACK 共同增加 `cwnd`，不是每收到一个 ACK 就把整个窗口翻倍。ACK 合并、延迟确认、应用受限、丢包和实现差异都会改变实际曲线。

经典 Reno 使用丢包驱动的 AIMD 思路；现代 Linux 常见 CUBIC 按时间函数增长，BBR 估计瓶颈带宽和往返传播时间。协议保证可靠字节流，但不规定所有实现必须使用同一拥塞算法。

#### 带宽时延积

要填满链路，允许的在途数据至少应接近：

```text
BDP = bandwidth × RTT
```

100Mbit/s、RTT 40ms：`100,000,000 × 0.04 / 8 ≈ 500,000` 字节，约 488KiB。若有效窗口只有 64KiB，单连接理论吞吐上限约为 `64KiB / 0.04s ≈ 1.6MiB/s`，远低于 100Mbit/s。实际还受丢包、应用读写和协议开销影响。

#### 连接关闭与 TIME_WAIT

TCP 是全双工，两个方向独立关闭，所以常见 FIN/ACK 往返看起来像四次。主动关闭方通常进入 TIME_WAIT，用来吸收旧报文并在最终 ACK 丢失时重发。大量 TIME_WAIT 本身不是故障；要结合短连接率、端口范围、连接复用和真正的新建连接失败判断。

### UDP

UDP 保留数据报边界，无连接建立，不保证可靠、有序、不重复，也没有 TCP 的流量/拥塞控制语义。低首部开销不等于应用一定更快：可靠性、分片、重传、拥塞与安全如果需要，必须由应用或上层协议实现。

### QUIC

QUIC 在 UDP 之上实现可靠传输、TLS 1.3 和多路流，是 HTTP/3 的基础。它把丢包影响限制在相关流、支持连接迁移，并减少部分握手往返；但 UDP 路径质量、加密 CPU、实现与运维支持仍需考虑。

### DNS

常见解析顺序：应用/浏览器缓存 → 操作系统缓存与 hosts → 递归 DNS → 根、顶级域、权威 DNS。缓存命中时不会每次都访问完整层级。

- Stub resolver：应用/系统的轻量入口。
- Recursive resolver：替客户端递归查询并缓存。
- Authoritative server：给出域名区域的权威记录。
- TTL：缓存有效期，不保证全球在同一时刻切换。
- Negative caching：不存在结果也可能被缓存。

CNAME 形成别名链，最终仍需解析 A/AAAA 等地址记录；MX、TXT、SRV 等服务于不同协议。DNS 轮询不等同于实时健康检查。

### TLS 1.3

TLS 提供身份认证、机密性和完整性。简化握手为：ClientHello 携带版本、套件、SNI、ALPN 与 key share；服务端选择参数并发送证书和签名；客户端验证域名、证书链、有效期与签名；双方通过（EC）DHE 等计算共享密钥并校验 Finished。

证书不负责“用公钥加密全部网页”。0-RTT 可降低恢复连接延迟，但存在重放风险，只适合可安全重放的操作。

### HTTP 与 HTTPS

- HTTP/1.1：持久连接、Host、分块传输等。
- HTTP/2：二进制分帧、单连接多路复用、HPACK 头压缩。
- HTTP/3：基于 QUIC，减少传输层队头阻塞。
- HTTPS：HTTP 运行在 TLS 之上，提供机密性、完整性和身份认证。

HTTP/2 Server Push 已被主流浏览器移除或停用，不应作为新的性能方案；优先使用缓存、预加载和合理资源拆分。

HTTP 方法、状态码、字段和缓存属于语义；HTTP/1.1 文本消息、HTTP/2 帧与 HTTP/3 QUIC 流是承载方式。升级版本不会自动解决缓存键、权限、幂等和超时错误。

## 高阶知识

### 一次 HTTPS 请求

```text
URL 解析
→ DNS 查询
→ 路由/ARP
→ TCP 握手（HTTP/3 则为 QUIC）
→ TLS 握手与证书验证
→ HTTP 请求
→ 反向代理与应用处理
→ HTTP 响应
→ 连接复用或关闭
```

TLS 1.3 的握手细节不同于旧版“客户端用证书公钥直接加密一个随机数”的简化描述。现代 TLS 通常使用（EC）DHE 协商共享密钥，以获得前向保密。

### 超时分层

- 连接超时：无法建立 TCP/QUIC 连接。
- TLS 超时：握手或证书链处理异常。
- 读取超时：连接已建立，但对方未及时返回数据。
- 上游超时：代理等待应用或依赖超时。

所有层都重试会造成重试风暴。应明确由哪一层重试，限制次数，使用退避和抖动，并保证操作幂等。

### 容量计算：平均在途请求

稳定系统可用 Little's Law 粗估：

```text
average_concurrency ≈ request_rate × average_response_time
```

若 500 RPS、平均响应 80ms，平均在途约 `500 × 0.08 = 40`。它不代表只需 40 个连接或 worker：长尾、突发、keepalive、上游连接和安全余量仍要单独计算。

### 长轮询、SSE 与 WebSocket

- 长轮询：服务器暂不响应，直到有数据或超时；兼容性好，连接开销较大。
- SSE：服务器到客户端的单向文本事件流，自动重连，适合通知和 AI 流式输出。
- WebSocket：全双工长连接，适合互动和双向实时通信。

## 使用案例

### 判断 502 与 504

- 502 Bad Gateway：代理未获得有效上游响应，例如上游拒绝连接、协议错误、进程崩溃。
- 504 Gateway Timeout：代理连接或等待上游响应超过超时。

查看 Nginx error log 中的 `connect() failed`、`upstream timed out`、`prematurely closed connection`，再检查对应上游。

### 验证 DNS

```bash
dig example.com
dig +trace example.com
getent hosts example.com
```

`dig` 查询 DNS；`getent` 更接近应用经系统名称服务获取的结果，可能包含 hosts。

### 查看 TCP 窗口与拥塞状态

```bash
ss -ti dst 203.0.113.10
sysctl net.ipv4.tcp_congestion_control
sysctl net.ipv4.tcp_available_congestion_control
```

`ss -ti` 可看到 RTT、拥塞窗口、重传等连接级信息，字段随内核版本变化。排查吞吐低时同时检查 RTT、丢包、`cwnd`、接收窗口和应用是否持续供数。

## 常见问题与排查

| 现象 | 优先证据 | 常见边界 |
|---|---|---|
| 域名无法解析 | 系统解析结果、递归 DNS 返回、权威记录、TTL | hosts、负缓存、DNSSEC、分流解析 |
| Connection refused | 目标 IP/端口、RST、监听 socket、代理目标 | 请求已到主机但无监听或被主动拒绝 |
| Connection timed out | 路由、ARP/NDP、安全组、防火墙、SYN 是否有回包 | 丢弃、错误路由、链路不可达 |
| 建连后读取超时 | 服务日志、TTFB、上游耗时、零窗口/重传 | 应用慢、依赖慢、接收端不读 |
| 单连接吞吐低 | RTT、丢包、`rwnd/cwnd`、flight、应用供数 | BDP 不足、窗口/拥塞、限速 |
| 小请求成功、大请求卡住 | MTU、ICMP Packet Too Big、隧道开销 | PMTU 黑洞或分片问题 |
| 502 | Nginx error log、上游拒绝/断开/协议错误 | 无有效上游响应 |
| 504 | 网关等待时间、上游队列、依赖超时 | 上游在预算内未完成 |

推荐顺序：确认名称 → 目标 IP → 路由/链路 → 端口与握手 → TLS → HTTP → 代理/应用。只在证据指向时调整 MTU、内核参数或队列。

## 常见误区

- “滑动窗口就是拥塞窗口”：错误；`rwnd` 保护接收端，`cwnd` 保护网络，有效发送还要扣除在途数据。
- “慢启动每收到 ACK 就翻倍”：错误；大致翻倍是一个 RTT 内 ACK 累积的结果。
- “UDP 一定比 TCP 快”：错误；取决于应用是否需要自己实现可靠、拥塞与安全。
- “TIME_WAIT 越少越好”：错误；它承担协议保护，应先判断是否真的端口耗尽或短连接异常。
- “ping 不通就是服务不可用”：错误；ICMP 可能受策略限制，而 TCP/UDP 服务仍可用，反之也成立。
- “HTTP/2 没有队头阻塞”：只消除了 HTTP/1.1 应用层顺序问题，TCP 丢包仍影响同连接全部流。

## 自测题与参考答案

1. **`10.0.0.0/20` 有多少 IPv4 地址？** `2^(32-20)=4096`。传统普通子网常说 4094 个主机地址，但特殊前缀不能一律减 2。
2. **为什么访问远端服务器时 ARP 的通常是网关？** 远端 IP 不在本链路，Ethernet 只负责把当前帧交给下一跳网关。
3. **1500 MTU 下 IPv4 TCP MSS 一定是 1460 吗？** 不一定；1460 假设无 TCP 选项且路径 MTU 为 1500，隧道和更小路径 MTU 会降低它。
4. **`rwnd=512KiB`、`cwnd=192KiB`、flight=160KiB，还能新发多少？** 约 `min(512,192)-160=32KiB`，未计实现和缓冲限制。
5. **1 Gbit/s、RTT 80ms 的 BDP 是多少？** `1,000,000,000×0.08/8=10,000,000` 字节，约 9.54MiB；单连接需要相近在途能力才能接近满带宽。
6. **重复 ACK 和 RTO 有何不同？** 重复 ACK 可较早提示局部丢段并触发快速重传；RTO 是缺少足够 ACK 线索后的计时器恢复路径。
7. **502 与 504 的关键区别？** 502 是代理没有获得有效上游响应，504 是等待上游超过预算；最终以代理日志和上游状态取证。
8. **HTTP/3 为什么使用 UDP 仍然可靠？** QUIC 在 UDP 之上实现确认、重传、拥塞控制、TLS 和流；可靠性来自 QUIC，不是 UDP。
9. **平均 1000 RPS、平均 50ms 时平均并发是多少？** 约 50；长尾和突发决定的容量可能明显更高。
10. **小包正常、大包卡住首先怀疑什么？** 检查 PMTU、ICMP Packet Too Big/Fragmentation Needed、隧道开销和防火墙对 ICMP 的错误过滤。
