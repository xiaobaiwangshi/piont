# 设计原则与设计模式

## 基础知识

设计模式是反复出现的设计问题的命名经验，不是必须套用的代码模板。先识别变化点和真实重复，再选择模式；一个实现、一个场景时通常不需要工厂、策略注册中心或复杂容器。

### 常用原则

- 单一职责：一个模块只有一个主要变化原因。
- 开闭原则：新需求优先通过扩展完成，但不意味着禁止修改旧代码。
- 里氏替换：子类型必须满足父类型承诺，不能破坏调用者预期。
- 接口隔离：调用者只依赖需要的能力。
- 依赖倒置：高层业务依赖稳定抽象，不绑定基础设施细节。
- 组合优于继承：组合能减少脆弱的层级耦合，但不是绝对规则。
- 最少知识原则：减少对象之间不必要的内部结构暴露。

### 三类 GoF 模式

| 类型 | 模式 |
|---|---|
| 创建型 | 单例、工厂方法、抽象工厂、建造者、原型 |
| 结构型 | 适配器、桥接、组合、装饰器、外观、享元、代理 |
| 行为型 | 责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者 |

“简单工厂”常被使用，但不属于 GoF 23 种模式；它仍是有用的创建技巧。

## 高阶知识

### 服务端最常用的模式

#### 责任链

请求按顺序经过多个处理器。Nginx 阶段处理、Gin/ThinkPHP 中间件都可理解为责任链。

适合：鉴权、限流、日志、参数校验。注意：链过长会隐藏控制流，应保持顺序清晰。

#### 策略

把可替换算法封装为统一能力，例如支付方式、促销规则、存储后端。

适合：确实存在多个算法并需要运行时选择。只有一个实现时直接调用更简单。

#### 适配器

把第三方接口转换为业务需要的接口。例如统一阿里云 OSS 与 S3 的上传能力。

适合：接口不兼容或隔离供应商 SDK。不要为了“将来可能换供应商”提前包装所有 API。

#### 装饰器

在不改变核心对象的情况下叠加行为，例如缓存、重试、指标和日志包装器。装饰顺序会影响语义：先缓存再重试与先重试再缓存并不相同。

#### 观察者

状态变化后通知多个订阅者。进程内事件适合低成本解耦；跨服务事件应使用可靠消息、事件表或 CDC，不能把内存回调当成可靠消息系统。

#### 状态

对象行为随状态变化，例如订单的待支付、已支付、已退款。状态转换应显式校验，避免任意赋值。

### 依赖注入与控制反转

- 控制反转：对象创建与装配权从业务代码转交给外部机制。
- 依赖注入：通过构造函数、方法或属性提供依赖，是实现控制反转的一种方式。
- 容器：保存绑定规则并解析对象图，是工具而不是业务架构。

优先构造函数注入：依赖明确、对象创建后有效、测试替换简单。服务定位器式的全局 `container()->get()` 会隐藏依赖，应谨慎使用。

### Go 的组合与接口

Go 内嵌提供字段/方法提升，不是继承。外层类型和内嵌类型没有“父子类”关系；接口由方法集隐式实现，适合在使用方定义小接口。

“接收接口，返回具体类型”是实用经验，不是铁律。跨包 API 若必须隐藏实现或允许多实现，也可能返回接口；关键是调用方是否需要抽象。

### 从问题选择模式

| 真实问题 | 可考虑的模式 | 不应引入的情况 |
|---|---|---|
| 多种算法需要切换 | 策略 | 只有一个稳定实现 |
| 第三方接口不符合业务语义 | 适配器 | 只是给同名方法再包一层 |
| 横切能力按顺序组合 | 装饰器/责任链 | 顺序和退出条件无法说明 |
| 对象行为由有限状态决定 | 状态 | 只有布尔开关且没有转换规则 |
| 一次动作需要排队、撤销或审计 | 命令 | 普通函数调用已经足够 |
| 一个事实触发多个后续动作 | 观察者/事件 | 需要强一致却只用内存通知 |

先写出变化点、不变量和失败边界，再选择模式。模式名称不能替代事务、幂等、超时或消息可靠性设计。

## 使用案例

### 支付策略

```php
interface PaymentGateway
{
    public function pay(int $amountInCents): string;
}

final class CheckoutService
{
    public function __construct(private PaymentGateway $gateway) {}

    public function checkout(int $amountInCents): string
    {
        return $this->gateway->pay($amountInCents);
    }
}
```

接口的价值是业务确实支持多支付渠道，且测试需要替代外部支付；如果永远只有一个本地函数，不必引入接口。

### Web 中间件

```text
Request
→ RequestId
→ Recovery
→ Authentication
→ RateLimit
→ Handler
→ Response
```

日志中间件应在外层以记录整个请求；恢复中间件需要覆盖可能 panic/throw 的下游；鉴权应在业务处理之前。

## 常见问题与排查

- 类数量暴涨：检查是否为单实现接口、无意义工厂或过细分层。
- 循环依赖：重新划分职责，提取稳定的小接口或事件，而不是让容器延迟解析掩盖问题。
- 业务规则散落：用状态机、策略或领域服务集中不变量。
- 事件丢失：进程内观察者不可靠；跨进程改用事务消息、outbox 或 CDC。
- 单例污染测试：显式注入依赖，避免可变全局状态。

## 版本边界与学习验收

GoF 模式和 SOLID 是设计语言，不依赖 PHP 版本；旧书中的 PHP 5 构造函数、访问控制边界、错误模型和动态属性行为不能直接当作 PHP 8.x 示例。现代 PHP 示例应使用显式类型、构造函数注入和可测试边界，但不要为了类型完整制造单实现接口。

验收：给一个真实业务变化点，先写“不使用模式”的最小方案，再说明何时演进为策略、状态或责任链；同时列出模式引入的类数量、控制流和测试成本。
