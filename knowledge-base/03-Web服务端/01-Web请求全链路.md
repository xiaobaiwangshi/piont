# Web 请求全链路

## 基础知识

### 从 URL 到响应

```text
客户端
→ DNS
→ TCP/QUIC 与 TLS
→ CDN/负载均衡
→ Nginx
→ PHP-FPM 或 Go 服务
→ Redis/MySQL/搜索/外部 API
→ 应用响应
→ Nginx/CDN
→ 客户端解析与渲染
```

每一跳都应定义：地址、协议、连接池、超时、最大请求大小、身份信息和失败行为。

### 浏览器收到响应之后

页面显示不是“下载完 HTML 就结束”。主流程可简化为：

```text
HTML 字节 → 解析并构建 DOM
CSS 字节  → 解析并形成样式规则
DOM + 样式 → 计算样式 → 布局 → 绘制 → 分层/合成 → 屏幕
```

- DOM 与可视对象通常不是一一对应：`display: none` 不进入布局树，伪元素和复杂控件可能产生额外绘制对象。
- JavaScript 可在解析过程中修改 DOM；同步脚本可能阻塞解析，样式表也可能影响脚本执行时机。
- 修改几何属性可能触发布局与绘制；只改变可合成的 transform/opacity 往往更便宜，但必须用浏览器性能工具验证。
- 现代浏览器通常采用多进程与沙箱：浏览器进程、网络进程、渲染进程和 GPU 进程分工，具体结构随浏览器版本变化。

因此 Web 性能要区分 DNS/网络、服务端 TTFB、资源下载、主线程长任务、布局/绘制与合成，而不是只看接口耗时。

### HTTP 核心语义

- GET：读取资源，应安全、幂等。
- POST：提交或触发处理，通常不幂等。
- PUT：用完整表示替换资源，通常幂等。
- PATCH：部分更新。
- DELETE：删除资源，语义上应幂等。

幂等是业务效果，不是由 HTTP 方法自动保证。支付、创建订单等需要幂等键、唯一约束和状态检查。

HTTP 语义与传输版本要分开理解。方法、状态码、字段和缓存语义由 HTTP 核心规范定义；HTTP/1.1 文本报文、HTTP/2 帧和 HTTP/3 QUIC 流只是承载方式。升级协议不会自动修复错误的缓存键、幂等或权限设计。

#### 消息边界

- HTTP/1.1 响应通常由无 body 的状态语义、`Content-Length`、chunked 编码或连接关闭确定边界；冲突的长度字段是安全风险。
- HTTP/2/3 用帧和流表达边界，不使用 HTTP/1.1 的 chunked 编码。
- HEAD、204、304 等响应的 body 规则需按规范处理，不能仅凭是否存在 `Content-Length` 判断。

### 状态码

- 2xx：成功。
- 3xx：重定向或缓存协商。
- 4xx：请求在当前语义下有问题，如 400、401、403、404、409、422、429。
- 5xx：服务端或网关失败，如 500、502、503、504。

401 表示缺少或无效认证；403 表示身份已知但无权限。不要所有业务错误都返回 200。

### 请求数据与响应

服务端必须区分路径参数、查询参数、表单、JSON、文件和 Cookie。输入验证包含：类型、长度、格式、范围、枚举、权限和业务状态；只做非空校验不够。

## 高阶知识

### 超时预算

假设外部请求总预算 2 秒：

```text
网关 2.0s
应用 1.8s
数据库 0.3s
缓存 0.05s
外部 API 0.8s
预留序列化、排队和网络时间
```

下游超时应小于上游预算。没有超时会导致资源长期占用；所有层设置相同超时会在边界集中失败。

### 重试、幂等与背压

- 只重试暂时性错误，例如连接重置、明确的 429/503。
- 使用指数退避和随机抖动。
- 写操作必须先保证幂等。
- 队列和连接池必须有上限；满载时限流、拒绝或降级，不能无限堆积。

### 缓存语义

- 浏览器/CDN：`Cache-Control`、ETag、Last-Modified。
- 反向代理缓存：按 URL、Header 和认证状态设计 cache key。
- 应用缓存：cache-aside 最常见，读取 miss 回源，写入时更新数据库并删除缓存。

敏感用户响应不能被公共缓存混用。`Vary` 和缓存键不完整会造成数据串读。

### 实时返回

AI 流式对话优先考虑 SSE：实现简单、单向流符合场景、浏览器原生支持。需要双向实时控制时再用 WebSocket。服务端应处理客户端断开、超时、取消、心跳和消息持久化。

## 使用案例

### API 请求处理

```text
解析请求
→ 生成/接收 request_id
→ 限制体积和速率
→ 认证
→ 参数验证
→ 幂等检查
→ 事务执行业务
→ 写事件/outbox
→ 提交事务
→ 返回统一响应
```

### 上传大文件

不要让单个 PHP 请求无限等待。使用客户端分片或云存储直传；服务端签发短期凭证、记录上传会话并在完成后校验对象大小、哈希、类型和归属。

### 优雅关闭

1. 从负载均衡摘除实例或让健康检查失败。
2. 停止接受新请求。
3. 等待在途请求至截止时间。
4. 停止消费者和后台任务。
5. 关闭连接并退出。

## 常见问题与排查

### 请求慢

用同一 request/trace ID 串联网关、应用、数据库与外部依赖。拆分 DNS、连接、TLS、TTFB 和下载时间；只看总耗时无法定位。

### 重复提交

检查客户端重试、代理重试、超时后响应丢失、消息重复投递。以业务幂等键和数据库唯一约束兜底，不依赖“客户端只点一次”。

### 请求体只能读取一次

HTTP body 是流。Gin 中多次绑定可使用 `ShouldBindBodyWith`，但会把 body 缓存在内存；大请求不应随意重复读取。更简单的方案是只绑定一次到明确结构体。

### 异步任务未完成

不要在请求结束后随手启动无管理 goroutine 或后台 PHP 进程。使用受控 worker/队列，记录任务状态、重试次数和失败原因。

## 版本边界与学习验收

- 稳定语义：方法安全性/幂等性、状态码、缓存条件请求、代理、认证和消息完整性。
- 版本相关：HTTP framing、头压缩、优先级、多路复用、QUIC、浏览器进程模型和渲染优化。
- 历史做法：HTTP/1.1 连接数优化不能原样套到 HTTP/2/3；HTTP/2 Server Push 不作为现代浏览器默认优化。

验收：用浏览器 Network/Performance 面板把一次页面加载拆成网络、TTFB、解析、长任务、布局和绘制；用 `curl -v` 对比条件请求、重定向和 HTTP 版本；解释 502、504 与浏览器渲染慢分别属于哪一段。
