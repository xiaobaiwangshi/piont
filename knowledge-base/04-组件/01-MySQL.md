# MySQL

## 学习目标与阅读方式

学完本章，应能从“SQL 语义 → 执行计划 → 索引页 → 事务与日志 → 复制和恢复”解释一次数据库操作，并能：

- 区分 MySQL Server 层与 InnoDB 存储引擎的职责。
- 估算 Buffer Pool 页框数、B+ 树扇出和树高，并说明估算边界。
- 判断索引访问、回表、排序、临时表和 join 的主要成本。
- 解释 MVCC、锁、redo、binlog、checkpoint 与 doublewrite 分别解决什么问题。
- 根据 RPO、RTO 选择复制与备份恢复方案。

建议先掌握 SQL、事务、操作系统缓存与磁盘 I/O 的基本概念。本文负责学习顺序、计算、使用案例和版本边界；页生命周期、日志协调等实现推理见[数据系统内部机制](../07-核心机制深入/05-数据系统内部机制.md)。文中的 SQL 和命令只用于解释知识，本阶段不要求连接数据库或执行实验。

## 基础知识

### 关系模型基础

关系表由行和列构成，候选键能唯一标识一行，选作主要标识的是主键；外键表达表间引用。范式用于减少重复与更新异常，但查询性能、历史快照和聚合场景可能需要有边界的反范式设计。数据库约束负责守住跨应用都必须成立的不变量，应用代码负责业务流程，二者不能互相完全替代。

SQL 是声明式语言：用户描述“要什么”，优化器决定“怎样访问”。因此同一条 SQL 在数据量、数据分布、统计信息或版本变化后，可能得到不同执行计划。

### SQL 与执行路径

MySQL 8.0 的典型查询路径：

```text
连接与权限
→ 解析器
→ 预处理/语义检查
→ 优化器生成执行计划
→ 执行器调用存储引擎
→ 返回结果
```

MySQL 8.0 已移除查询缓存，不能再把“先查 query cache”作为当前执行流程。

- DDL：定义结构，如 `CREATE`、`ALTER`。
- DML：读取和修改数据，如 `SELECT`、`INSERT`、`UPDATE`、`DELETE`。
- TCL：事务控制，如 `COMMIT`、`ROLLBACK`。
- DCL：权限控制，如 `GRANT`、`REVOKE`。

职责边界可概括为：

| 层次 | 主要职责 |
|---|---|
| MySQL Server 层 | 连接、认证、SQL 解析、优化、执行框架、binlog、存储过程等 |
| InnoDB | 表和索引页、Buffer Pool、事务、MVCC、行锁、redo/undo、崩溃恢复 |

优化器选择访问路径，执行器通过存储引擎接口取行；不能把 binlog 当作 InnoDB redo，也不能把 SQL 优化全部归于存储引擎。

### InnoDB

InnoDB 提供事务、行级锁、MVCC、崩溃恢复和聚簇索引。核心内存与日志：

- Buffer Pool：缓存数据页和索引页，也保存脏页。
- Redo Log：记录物理变更，用于崩溃恢复和持久性。
- Undo Log：保存旧版本，用于回滚和 MVCC。
- Binlog：Server 层逻辑日志，用于复制和审计恢复。

### InnoDB 页与 Buffer Pool

InnoDB 的常用物理组织层次是：

```text
表空间 → 段（segment）→ 区（extent）→ 页（page）→ 行记录（record）
```

- 表空间是页的逻辑容器，可包含表数据、索引或系统信息。
- 段按用途组织一棵索引的叶子页、非叶子页等空间。
- 区是一组连续页；默认 16KiB 页时，一个常见 1MiB 区包含 64 页。页大小可配置时必须重新计算，不能把 64 当作所有实例的常量。
- 页是 Buffer Pool、读取和刷新的主要单位；一次只需要一行，也可能读取整页。
- 行格式决定记录头、变长列、NULL 标记和长列在页内外如何存放。

InnoDB 以页为主要磁盘和缓存管理单位。默认页大小通常是 16KiB，可查询：

```sql
SHOW VARIABLES LIKE 'innodb_page_size';
```

可选页大小与创建实例/表空间方式、MySQL 版本有关，通常不能在已有实例上简单修改配置后直接切换。常见页类型包括索引页、undo 页、系统页和 blob/溢出页。

Buffer Pool 缓存的也是页，而不是独立的 SQL 查询结果。主要链表/结构可概括为：

- Free List：尚未使用、可装入新页的块。
- LRU List：缓存页的冷热顺序；InnoDB 分 young/old 区域，减少大范围扫描把热点页全部淘汰。
- Flush List：按最早修改 LSN 等信息组织脏页，供后台刷盘和 checkpoint 推进。

读取未命中时，从表空间把整页读入 Buffer Pool；修改先发生在内存页并产生 redo，脏页之后异步刷盘。提交事务通常不需要把所有数据页立即写盘。

#### Buffer Pool 能容纳多少页

粗略页框数量可按下式估算：

```text
buffer_pages ≈ innodb_buffer_pool_size / innodb_page_size
```

例如 Buffer Pool 为 8 GiB、页为 16 KiB，理论上约有 `8 × 1024³ / 16384 = 524288` 个页框。真实内存还包含控制结构、哈希、锁、连接、排序和 Performance Schema 等，不能把该公式当 mysqld 总内存。

若一张表的数据与索引共 100 GiB，8 GiB Buffer Pool 也不等于固定“命中 8%”：访问具有热点和局部性，上层索引页更容易常驻。观察应结合：

```sql
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_pages%';
```

常用粗略读命中率是 `1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests`，但累计计数会掩盖时间窗口变化，监控系统应计算速率并同时看磁盘延迟、脏页和工作集变化。

16KiB 页不表示一行必须完整占在同一页。DYNAMIC 等行格式会把长 `BLOB/TEXT` 或过长变长列的部分内容放到溢出页，行内保存指针；实际行为取决于行格式、列宽和版本。

COMPACT 把变长字段长度和 NULL 信息紧凑保存；DYNAMIC/COMPRESSED 更积极地把长列内容放到页外，行内通常保留引用。MySQL 5.7、8.0、8.4 的默认行格式和可用压缩方式受版本、表空间与配置影响，应以 `SHOW TABLE STATUS`、`information_schema` 和对应版本手册为准。

当目标页没有足够连续空间时，B+ 树可能分裂：分配新页、搬移记录并更新父节点。页分裂会增加写 I/O、redo、空间碎片和缓存扰动；删除记录后页也不一定立即归还文件系统，合并与空间回收取决于页利用率和表空间方式。顺序递增主键通常比随机宽主键更利于聚簇索引局部写入，但也可能形成最右页写热点。

#### 页生命周期与 checkpoint 压力

一次典型更新可按顺序理解：

```text
Buffer Pool 未命中 → 从表空间读页 → 在内存修改并生成 redo
→ 页成为脏页 → 后台刷盘 → checkpoint 推进 → 干净冷页可被淘汰
```

Free、LRU、Flush 不是三份页副本，而是从“可分配、冷热、脏页刷新顺序”等不同角度管理页。脏页产生速度长期高于刷新速度时，checkpoint 无法及时推进，可用 redo 空间缩小，后台刷新会加强，严重时前台写入被迫等待。命中率高也不能证明数据库健康，还要看物理读延迟、脏页比例、redo 使用速度和尾延迟。

### 表设计

- 选择能表达业务范围的最小合理类型，不为省几个字节牺牲可读性和未来范围。
- 金额使用整数最小单位或 `DECIMAL`，不用浮点数。
- `NULL` 是合法建模工具，不应机械禁止；需要明确“未知/不存在”是否与默认值不同。
- 外键能保证数据库级引用完整性，但在高吞吐或分库场景需评估写入、迁移和治理成本。
- JSON 适合结构变化且不需要强关系约束的数据；核心查询字段仍应显式建列，必要时使用生成列或多值索引。

## 索引

### B+ 树

InnoDB 默认页大小通常为 16KiB。B+ 树内部节点主要存键和子页指针，叶子节点存记录或主键，因此扇出高、树高低、范围扫描顺序友好。

“三层能存多少行”只能估算：它取决于主键宽度、记录大小、页头、槽目录、填充率、变长字段和页分裂，不能用一个固定公式当作准确容量。

#### 结构图

```text
                         [根页：分隔键 + 子页号]
                      /              |              \
          [内部页 <1000]      [内部页 1000..]       [内部页 ...]
             /      \              /       \
      [叶子页] <-> [叶子页] <-> [叶子页] <-> [叶子页]
      完整行记录      完整行记录      完整行记录       完整行记录
```

聚簇索引叶子页保存完整行，并通过相邻页关系支持范围扫描；内部页保存分隔键和子页号。二级索引叶子页保存“二级索引键 + 主键”，需要其他列时再按主键回到聚簇索引，这就是回表。

#### 层高计算方法

先定义：

```text
P = 单页可用于记录的字节数
E = 内部节点每个目录项平均字节数（键 + 子页号 + 记录/槽开销）
R = 叶子节点每行平均占用字节数
F = floor(P / E)       # 内部节点扇出
L = floor(P / R)       # 每个叶子页行数
高度 h 的容量约为 F^(h-1) × L
```

页总大小默认 16384 字节，但要扣除页头、页尾、槽目录和预留空间，且页通常不会永远 100% 填满。下面仅作数量级估算。

假设：

- BIGINT 主键 8 字节。
- 子页号及记录/槽开销合计后，内部项按 16-20 字节估算。
- 可用空间按约 14KiB 估算。
- 聚簇索引平均每行约 1KiB。

则：

```text
F ≈ 14336 / (16~20) ≈ 716~896
L ≈ 14336 / 1024 ≈ 14 行

高度 1：14 行                         # 根页就是叶子页
高度 2：716~896 × 14 ≈ 1.0万~1.25万行
高度 3：(716~896)^2 × 14 ≈ 718万~1124万行
高度 4：(716~896)^3 × 14 ≈ 51亿~100亿行
```

因此按“每行约 1KiB”的保守假设，一亿行聚簇索引通常需要 4 层。若行只有约 200 字节，单叶子页能放约 70 行，高度 3 的容量可提高到约 3600万~5600万，仍可能需要第 4 层；若内部项更小、填充率更高，结果还会变化。

网上常见 `1170 × 1170 × 16 ≈ 2190 万行`，是假设内部项约 14 字节、叶子每页 16 行且页面接近满载的理想估算。它可以解释数量级，不能预测某张真实表。

#### 树高不等于物理磁盘 I/O 次数

查找一行在逻辑上会访问每层页面，但根页和上层内部页几乎总是热点，通常已在 Buffer Pool 中；叶子页也可能命中缓存。因此 4 层树不代表每次查询必做 4 次物理磁盘读取。

二级索引非覆盖查询可能先遍历二级 B+ 树，再按主键遍历聚簇 B+ 树；逻辑页访问会更多。覆盖索引能省掉回表，但会增加索引空间和写入维护成本。

#### 真实表如何估算

```sql
SELECT table_name, table_rows, data_length, index_length
FROM information_schema.tables
WHERE table_schema = 'your_db' AND table_name = 'your_table';

SHOW INDEX FROM your_table;
```

`table_rows` 对 InnoDB 常为估算值。需要更准确时结合实际数据量、`INNODB_INDEX_STATS`、页检查工具和测试环境验证，不直接读取生产页做破坏性实验。

`mysql.innodb_index_stats` 中的 `size`、`n_leaf_pages` 和前缀基数可帮助估算页数与选择性，但它们是统计信息，不直接保证精确树高。可先用 `n_leaf_pages` 和扇出估算层数，再在副本/测试环境用页检查工具验证。

### 索引类型

- 聚簇索引：叶子保存整行，InnoDB 通常按主键组织。
- 二级索引：叶子保存索引列和主键，查询其他列时可能回表。
- 唯一索引：保证非 NULL 组合的唯一性；NULL 语义需按版本和业务验证。
- 联合索引：多个列共同排序。
- 覆盖索引：所需列均可由索引返回，避免回表。
- 前缀索引：索引字符串前缀，节省空间但能力受限。
- 全文索引：基础全文搜索；复杂搜索通常考虑专用搜索引擎。

### 最左前缀与失效

联合索引 `(a, b, c)` 按 a、b、c 排序，可有效支持从最左列开始的查找。范围条件后的列不一定完全“失效”：MySQL 仍可能用索引条件下推过滤，具体以执行计划和实际执行统计为准。

常见不利因素：

- 对索引列做函数或隐式类型转换。
- 前导通配符 `LIKE '%x'`。
- 条件选择性太低，优化器判断全表扫描更便宜。
- OR 分支缺乏合适索引。
- 排序/分组顺序与索引不匹配。

`IS NULL`、`!=`、范围查询并非必然不用索引；不要背“索引失效清单”，要用数据分布和 `EXPLAIN ANALYZE` 验证。

### 选择性、统计信息与访问方法

选择性可粗略表示为 `不同值数量 / 总行数`。高选择性条件通常更适合索引点查，但联合索引还要考虑列顺序、范围、排序、覆盖和实际查询组合。优化器使用采样统计、基数估算和代价模型，而不是读取全部数据后再选计划；统计信息陈旧或数据倾斜会导致估算偏差。

MySQL 8.0 支持直方图辅助描述非索引列等数据分布；直方图能改善特定谓词估算，不会直接加速取数，也不能替代索引。5.7 没有同等的 8.0 直方图能力。

- ICP（Index Condition Pushdown）：在存储引擎读取索引项时尽早判断可下推条件，减少无效回表；不等于覆盖索引。
- MRR（Multi-Range Read）：把多个二级索引命中的主键按更利于访问数据页的顺序读取，以减少随机 I/O；是否采用由成本模型决定。
- join：MySQL 常通过嵌套循环及其优化变体连接数据；驱动侧行数、被驱动表索引和中间结果决定成本。8.0 的具体 join 算法随小版本演进，5.7 与 8.0 不应套用同一结论。
- filesort：表示不能完全按目标索引顺序返回，需要额外排序；它不一定真的写磁盘，小结果可能在内存完成。
- 临时表：用于部分分组、去重、排序或派生结果；是否落盘取决于大小、字段类型、参数和版本。

判断执行计划时，应把 `rows`、过滤率等估算与实际行数、循环次数和耗时对照。`EXPLAIN ANALYZE` 从 MySQL 8.0.18 起可用且会真实执行语句；5.7 只能结合 `EXPLAIN`、状态计数和慢日志等证据，不能直接照搬。

## 事务与并发

### ACID

- 原子性：undo 与事务机制保证全部成功或回滚。
- 一致性：由约束、事务逻辑和正确应用共同维护。
- 隔离性：锁与 MVCC 控制并发可见性。
- 持久性：redo、刷盘策略和存储可靠性共同保证。

### 隔离级别

- READ UNCOMMITTED：可能脏读。
- READ COMMITTED：每次一致性读通常创建新 Read View，可能不可重复读。
- REPEATABLE READ：事务内一致性读通常复用 Read View；InnoDB 结合 next-key lock 处理锁定读的幻影问题。
- SERIALIZABLE：更强隔离，并发能力更低。

MVCC 主要服务普通一致性读；写操作和 `SELECT ... FOR UPDATE` 仍涉及锁。

### Read View、版本链与锁

InnoDB 聚簇记录包含事务相关隐藏信息；更新产生的 undo 把旧版本串成版本链。一致性读依据 Read View 判断哪个版本可见：READ COMMITTED 通常每条一致性读创建新视图，REPEATABLE READ 通常在事务首次一致性读时创建并复用视图。Read View 解决可见性，不负责阻止其他事务修改数据。

- 一致性读：普通 `SELECT` 通常读取快照，不为命中记录加排他锁。
- 锁定读：`SELECT ... FOR UPDATE/FOR SHARE` 读取当前可见数据并加锁。
- record lock：锁索引记录。
- gap lock：锁索引记录之间的间隙，本身不锁已有记录，主要抑制范围内插入。
- next-key lock：记录锁与其前间隙的组合，是 InnoDB REPEATABLE READ 范围锁定的重要形式。

锁作用在索引访问路径上；缺少合适索引可能扫描并锁住远多于业务预期的范围。READ COMMITTED 通常减少 gap locking，但唯一性检查、外键检查等仍有例外。死锁是并发事务形成等待环，不等于数据库坏掉；应保留短事务、统一访问顺序、合适索引，并让应用能够重试被选作牺牲者的事务。

### 两阶段锁

两阶段锁协议要求先获取锁、后进入只释放锁的阶段，可保证冲突可串行化。严格两阶段锁把写锁持有到提交。它并不“减少死锁”；持锁等待本身可能产生死锁，数据库需要检测并回滚一个事务。

### 提交流程简图

事务修改页时产生 undo/redo，页在 Buffer Pool 中变脏；提交涉及 redo 与 binlog 的协调（两阶段提交），以减少崩溃后两类日志不一致。脏页通常由后台线程稍后刷盘，提交不要求立刻把所有数据页写回磁盘。

### 日志、checkpoint 与崩溃恢复

各机制解决的问题不同：

| 机制 | 主要作用 | 不是用来做什么 |
|---|---|---|
| undo | 回滚、构造 MVCC 旧版本 | 不是复制日志 |
| redo | 重做尚未写回数据页的 InnoDB 变更 | 不是完整 SQL 历史 |
| binlog | Server 层变更事件，用于复制和时间点恢复 | 不能单独修复 torn page |
| checkpoint | 标记恢复起点并推动脏页落盘、复用 redo 空间 | 不等于每次提交刷数据页 |
| doublewrite | 避免数据页写一半造成 torn page | 不替代 redo 或备份 |

启用 binlog 时，InnoDB redo 与 Server 层 binlog 通过 prepare/commit 协调。group commit 让多个事务共享部分日志刷盘成本，提高吞吐；最终持久性还受 `innodb_flush_log_at_trx_commit`、`sync_binlog`、操作系统和存储设备写入保证影响。

崩溃启动时可按“定位 checkpoint → 用 redo 重放已持久化日志中的页变更 → 回滚未提交事务 → 继续后台清理”理解。redo 负责把页推进到正确状态，undo 负责撤销未提交逻辑；doublewrite 在读取数据页发现撕裂时提供完整页来源。精确阶段和并行方式随版本变化。

## 高阶知识

### 执行计划

重点看：

- 实际访问行数与估算是否偏差大。
- 访问类型和使用的索引。
- join 顺序与驱动表。
- 是否临时表、文件排序、回表过多。
- 过滤率、循环次数和实际耗时。

MySQL 8.0 优先使用 `EXPLAIN ANALYZE` 获取实际执行数据；它会真实执行语句，写操作和重查询要谨慎。

### 复制与新增从库

新增大库副本的安全路径：

1. 检查版本、GTID、binlog 格式、磁盘、网络和复制账户。
2. 使用物理备份工具或云快照获取一致性备份，避免对主库长时间锁表。
3. 在新从库恢复备份。
4. 从备份位点/GTID 接入复制。
5. 观察复制延迟、I/O、CPU 和错误。
6. 追平后再加入读流量。

新从库追赶会增加主库 binlog 发送、网络和磁盘读取压力，但“复制延迟”本身不会反向阻塞主库提交；具体影响取决于半同步、网络、存储和资源竞争。100GB 只是容量，变更速率和恢复带宽更决定追赶时间。

### GTID、复制与备份恢复边界

GTID 为已提交事务提供全局标识，简化故障切换和接续位点管理，但不会自动保证零数据丢失、拓扑正确或应用重试安全。异步复制在主库确认提交时通常不等待从库收到日志，故障时可能丢失尚未复制的事务；半同步通常只确认至少一个从库收到并持久化到其中继日志等阶段，不等于从库已执行，也不等于跨节点强一致。

复制是高可用和读扩展手段，不是备份：误删、坏数据和部分逻辑错误也会复制。备份策略至少要同时定义：

- 逻辑备份：可移植、可选择对象，恢复大库通常较慢，并需处理一致性与对象依赖。
- 物理备份/快照：大库恢复通常更快，但依赖版本、存储格式和一致性流程。
- binlog：在全量备份后推进到指定时间点，用于 PITR。
- RPO：最多能接受丢失多长时间的数据；决定备份、binlog 归档和复制要求。
- RTO：最多能接受恢复多久；取决于取回、恢复、重放、校验和切流的总时长。

“有备份”不等于“能恢复”。必须定期验证备份可读、版本兼容、密钥可用、binlog 链连续，并记录恢复后如何校验行数、关键业务数据与复制位点。本章只整理这些决策，不执行恢复演练。

## 常见问题与排查

### CPU 高

查看活跃会话、慢 SQL、执行计划变化、扫描行数、并发、锁等待和 Buffer Pool 命中。不要看到 CPU 高就先增加连接数。

### 锁等待/死锁

MySQL 8.0 使用 `performance_schema.data_locks`、`data_lock_waits` 和 `SHOW ENGINE INNODB STATUS`；旧的 `INFORMATION_SCHEMA.INNODB_LOCKS` 已被替代。

### 复制延迟

检查大事务、DDL、单线程热点、从库磁盘/CPU、网络和并行复制配置。拆小事务、避免主键缺失，并先解决资源瓶颈。

## 常见误区

1. **16KiB 页等于一行 16KiB**：错误。页包含多行、管理开销，长列还可能使用溢出页。
2. **B+ 树四层等于四次磁盘 I/O**：错误。逻辑访问的页可能已在 Buffer Pool。
3. **命中率 99% 就没有 I/O 问题**：错误。累计值会掩盖短时读放大、脏页刷新和尾延迟。
4. **加索引只会让查询更快**：错误。索引占空间，并增加插入、更新、删除、redo 和缓存压力。
5. **filesort 一定写磁盘**：错误。它表示额外排序，是否落盘取决于数据和配置。
6. **REPEATABLE READ 下所有读都相同**：错误。一致性读与锁定读语义不同。
7. **MVCC 不需要锁**：错误。写入、唯一性检查和锁定读仍需锁。
8. **redo 和 binlog 二选一即可**：错误。二者层次、格式和用途不同。
9. **半同步复制等于零丢失强一致**：错误。确认阶段、超时退化与故障窗口必须单独分析。
10. **复制副本就是备份**：错误。逻辑错误会传播，且副本不能替代历史版本和恢复验证。

| 主题 | 5.7 | 8.0 | 8.4 LTS |

## 学习验收

### 自测题

1. Server 层与 InnoDB 各负责哪些核心工作？
2. 8GiB Buffer Pool、16KiB 页理论上约有多少页框？为什么不是 mysqld 总内存？
3. 假设可用页空间 14KiB、内部项 20B、叶子记录 500B，估算扇出、每叶子页行数和三层树容量。
4. 聚簇索引、二级索引和覆盖索引的叶子分别保存什么？
5. 选择性高是否一定使用索引？直方图是否会直接加速读取？
6. 一致性读与锁定读有何区别？READ COMMITTED 与 REPEATABLE READ 的 Read View 有何典型差异？
7. record、gap、next-key lock 的边界是什么？
8. redo、binlog、checkpoint、doublewrite 各解决什么问题？
9. 半同步复制为什么不等于强一致？复制为什么不等于备份？
10. RPO 为 5 分钟、RTO 为 30 分钟分别约束什么？方案中至少要具备哪些能力？

### 参考答案

1. Server 层负责连接、SQL 解析优化执行框架与 binlog；InnoDB 负责页、索引、事务、MVCC、锁、redo/undo 和恢复。
2. `8 × 1024³ / 16384 = 524288` 页；总内存还包括页控制结构、连接、排序、锁、Performance Schema 等。
3. `F=floor(14336/20)=716`，`L=floor(14336/500)=28`，三层容量约 `716²×28≈1435 万行`；未计填充率、页目录、变长记录和分裂，只有数量级意义。
4. 聚簇叶子保存完整行；二级叶子保存二级键与主键；覆盖索引是查询所需列可直接从某索引得到，并非独立物理类型。
5. 不一定，还取决于返回比例、回表、排序、统计与成本；直方图改善基数估算，不直接存取数据。
6. 一致性读按快照读旧版本，锁定读读当前版本并加锁；RC 通常每条一致性读新建视图，RR 通常事务内复用首次一致性读的视图。
7. record 锁已有索引记录，gap 锁记录间隙，next-key 是记录与其前间隙的组合；具体加锁由隔离级别、索引路径和谓词决定。
8. redo 重做页修改，binlog 支持复制/PITR，checkpoint 推进可恢复边界并复用 redo，doublewrite 防 torn page。
9. 半同步确认收到日志不代表从库已执行，且存在超时/故障窗口；复制会传播误操作，不能提供独立历史恢复点。
10. RPO 限制最多丢 5 分钟数据，RTO 限制 30 分钟内恢复服务；至少需要满足频率的备份/binlog 归档、足够快的恢复路径、校验和切流流程。
