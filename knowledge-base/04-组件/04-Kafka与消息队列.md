# Kafka 与消息队列

原始资料只零散提到消息队列，本篇补齐服务端架构所需的核心知识。

## 基础知识

消息队列用于异步化、削峰、解耦和事件传播。它不会自动提高所有系统的可用性：队列引入了积压、重复、乱序、消息丢失和运维成本。

### Kafka 核心模型

- Broker：Kafka 服务节点。
- Topic：消息逻辑分类。
- Partition：有序追加日志和并行度单位。
- Replica：分区副本。
- Producer：写入消息。
- Consumer Group：组内消费者分摊分区。
- Offset：消费者在分区中的位置。

Kafka 只保证单分区内顺序，不保证整个 Topic 全局顺序。需要同一业务实体有序时，用稳定 key 把其消息路由到同一分区。

### RabbitMQ 核心模型

```text
Producer → Exchange --binding/routing key→ Queue → Consumer
```

- direct：路由键精确匹配。
- topic：按点分词的模式匹配。
- fanout：广播到绑定队列。
- headers：按消息头匹配，使用相对少。

交换器负责路由，队列负责保存和投递；消息持久化、持久队列、publisher confirm 和副本策略要共同设计，单独设置 `delivery_mode=2` 不能覆盖所有丢失窗口。

### RabbitMQ/Redis Stream/Kafka 选择

| 场景 | 倾向选择 |
|---|---|
| 高吞吐事件流、日志、可重放 | Kafka |
| 复杂路由、任务命令、低延迟确认 | RabbitMQ |
| 已有 Redis、规模适中、简单消费者组 | Redis Stream |
| 云上减少运维 | 托管消息服务 |

以团队能力、语义和容量选择，不只看峰值吞吐榜单。

## 高阶知识

### 可靠性

生产者可靠性取决于 `acks`、重试、幂等生产者和副本配置。消费者通常采用：

```text
拉取消息
→ 执行业务（必须幂等）
→ 成功后提交 offset
```

处理后、提交前崩溃会重复消费；提交后、处理前崩溃会丢业务处理。常见系统选择 at-least-once，再靠幂等解决重复。

Kafka 的 exactly-once 主要覆盖 Kafka 内的事务读写；一旦同时写 MySQL、调用 HTTP 等外部系统，仍需要业务事务、outbox、幂等和补偿。

RabbitMQ 需要区分两种确认：publisher confirm 告诉生产者 broker 是否接管消息；consumer ack 告诉 broker 消费是否完成。消费者在业务完成前 ack 会产生丢处理窗口，完成后 ack 则可能重复，因此业务同样需要幂等。

`prefetch` 限制单个 channel/consumer 未确认消息数量，是 RabbitMQ 背压的重要旋钮。值过大可能造成单消费者囤积和故障重投风暴，过小则无法覆盖处理延迟；按单任务成本、并发和内存实测。

### Outbox 模式

在同一个数据库事务中写业务表和 outbox 事件，后台发布器或 CDC 把事件送入 Kafka。这样避免“数据库成功但发消息失败”的双写窗口。

消费者用事件 ID/业务版本做去重；事件 Schema 应向后/向前兼容，不能随意删除字段或改变含义。

### 重试与死信

- 短暂错误：有限次数退避重试。
- 长期依赖故障：延迟队列/重试 Topic，避免阻塞主分区。
- 永久数据错误：死信队列，告警并提供修复重放工具。

无限重试会形成毒消息和积压。重放必须可审计、可限速、可停止。

RabbitMQ 使用 TTL + dead-letter exchange 实现延迟重试时，要防止消息在主队列与重试队列无限循环。记录重试次数、原始路由和最后错误；超过上限进入人工可观测的死信流程。

### 背压和积压

监控生产速率、消费速率、consumer lag、最老消息年龄和处理失败率。扩消费者只在分区足够且下游有容量时有效；否则会把压力推给数据库。

## 使用案例

### 订单事件

```text
订单事务：写 orders + outbox(order_created)
→ CDC/Kafka
→ 库存消费者
→ 通知消费者
→ 数据分析消费者
```

事件表示已经发生的事实，不应把可变数据库行原样当稳定事件协议。

### 视频转码任务

API 创建任务并返回 task_id；worker 消费后执行 FFmpeg，周期性更新进度，成功写产物，失败按错误类型重试。并发数按 CPU/GPU 和存储带宽限制，不能让队列消费者无限启动转码进程。

## 常见问题与排查

- Lag 增长：区分生产突增、消费者变慢、再均衡、单分区热点和下游瓶颈。
- 重复消息：正常设计目标之一，检查幂等键，不以“去掉重试”解决。
- 消息乱序：确认 key、分区变化、重试和并行处理。
- Rebalance 频繁：检查处理时间、心跳、实例抖动和分区分配策略。
- 磁盘增长：检查 retention、压缩策略、流量和副本数，不能直接删除 broker 数据目录。

## 版本边界与学习验收

- RabbitMQ 旧资料中的 classic mirrored queue 属于历史高可用方案；现代部署优先评估 quorum queue。Stream 适合大规模追加、保留和重放，但语义与普通 queue 不同。
- Kafka broker、controller/KRaft、producer defaults、consumer group 协议和事务行为会随大版本演进；部署必须绑定版本矩阵。
- “持久化 + ack = 绝不丢”“exactly-once = 外部业务恰好一次”都不成立，必须描述故障发生在哪个确认边界。

实验：让生产者在 confirm/ack 前后断开；让消费者在业务提交与 offset/ack 前后崩溃；记录重复、丢处理窗口、重投顺序和积压恢复速度，再验证幂等键与死信重放。
